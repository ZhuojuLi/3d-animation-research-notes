## 一句话结论

这是第三份返回的完整可见轨迹，对应 **Case 2：多轨时间编排与镜头**。它证明一个轻量的 `explosionAt(t) + cameraKeys + labelOpacity(t)` 已足够表达四段产品动画，不需要通用场景 IR 或重型时间线编辑器。

最有价值的工程经验有两条：

1. **多轨动画不能只检查零件位置，还要检查投影后的标签、UI 遮挡和相机矩阵更新时机。**
2. **局部修改有清晰接口，但 Case 5 的“只反转 6–9 秒镜头方向”仍需要专门验证 9–12 秒是否被连带改变。**

## 多轨时间编排

### 统一时间源

`sample(t)` 同时驱动零件、灯光、相机、标签和 UI。正常播放采用 1/60 秒累加步长，但场景状态仍由绝对时间计算，不是依赖历史状态的物理模拟。

### 爆炸进度

```text
e(t) = 0                                  t < 3
       smoothstep(3, 6, t)                3 ≤ t < 6
       1                                  6 ≤ t < 9
       1 - smoothstep(9, 12, t)           9 ≤ t ≤ 12
```

最终零件位移为：

| 模块 | 完全展开时的位移 |
|---|---|
| 底座 | `z = +3.4e`，向前滑出，便于从外壳下方看到 |
| 外壳 | `z = -1.6e`，向后 |
| 扬声器单元/前障板 | `z = +2.4e`，向前 |
| 控制面板 | `y = +1.6e`，向上 |
| 旋钮 | `y = +2.85e`，比面板更高 |

这些位移服务装配轴和画面可读性，而不是任意向外飞散。底座最初向后，因被外壳遮挡改为向前，见 `../references/kimi-probes/case-02-speaker/transcript.txt:2202-2240`。

### 灯光与标签

- 亮灯：`smooth(0.3, 2.65, t)`。
- 为支持循环，在 11.55–12 秒把灯光再淡回初始状态；这是额外为闭环做的处理，原需求没有强制循环。
- 标签：`smooth(5.85, 6.55, t) × (1 - smooth(8.55, 9.25, t))`，因此 t=6 时刚开始淡入，不应把“透明度尚低”误判为标签失效。

### 最终相机关键帧

| 时间 | 主要作用 | 最终参数摘要 |
|---|---|---|
| 0 | 初始全景 | r=12.8、θ=0.28、targetY=2.4 |
| 3 | 推近结束 | r=11.7、θ=0.16、targetY=2.48 |
| 6 | 展开全景 | r=23、θ=0.34、targetY=3.05 |
| 9 | 环绕后 | r=23.2、θ=1.08、targetY=3.05 |
| 12 | 返回初始 | 与 t=0 相同 |

这些数值来自多次看图调整，不是一次性拍脑袋设定。最终版增大了展开镜头距离、降低 target，并修正推近阶段的构图，见 `:2360-2379`。

## 零件间距与“没有穿插”的证据强度

轨迹进行了源码级间距推导：

- 外壳前端与前障板背面在装配时保留约 0.025 间隙，展开后差距只增大。
- 底座顶面与外壳底面约 0.04 间隙。
- 底座顶面与前障板底面约 0.19 间隙。
- 外壳顶面与面板底面保留小间隙。
- 面板和旋钮在展开时上升量不同，形成额外 1.25e 的间隔。

这与当前位移设计一致，但**仍不是独立的连续碰撞检测**。原轨迹没有实际包围盒/AABB/OBB 检查；本机随后补充了 11 个时刻、8 组非配合零件的实际 `Box3.setFromObject()` 检查，88 组均未相交。装配处的刻意嵌合不能用“所有包围盒不得相交”替代，因此明确排除了 shell/drivers 配合区和 panel/knob 接触；采样 AABB 仍不是全时段精确碰撞证明。

本机未来可把任务的零件尺寸、轴线和最小间隙写成轻量检查，在 3、6、9 秒及中间时刻验证；不需要引入物理引擎。

## 标签系统：一个真正的确定性 seek 陷阱

标签不是 Three.js 文本，而是：

- 3D anchor → `part.localToWorld()` → `camera.project()` 得到屏幕坐标。
- DOM 标签放在主体两侧留白。
- SVG 曲线连接标签和零件。
- 小屏幕改为底部三列信息网格，隐藏连线并进一步拉远相机。

最重要的 bug 是：seek 改变相机后，`camera.lookAt()` 尚未更新 `matrixWorldInverse`，标签立即投影，读到了**上一帧相机矩阵**。修复是在标签计算前显式：

```js
camera.updateMatrixWorld();
```

证据：`../references/kimi-probes/case-02-speaker/transcript.txt:2354-2379`。

这条应直接写入本机浏览器契约：**seek 后先更新所有依赖矩阵，再投影、截图和读回状态。** 即使 3D 主体正确，标签和屏幕空间测量也可能仍是旧状态。

标签文案还有一个小的内容问题：界面写“高低音同轴前障板”，但几何中 woofer 和 tweeter 的 y 坐标不同，实际是上下排列，不是同轴单元。功能不受影响，文案精度应改进。

## 浏览器验证与返修

### 浏览器环境

初始 Chromium 多次出现 WebGL context 创建失败。最终发现 `DISPLAY=:99` / Xauthority 导致图形初始化问题，使用：

```text
env -u DISPLAY -u XAUTHORITY ... chromium
```

后获得真实 WebGL。CLI 验证器仍曾出现截图失败、异常图片和首末差异，随后改用 Playwright 做真实截图和状态检查，见 `:1865-1967`。

这与 C1/C3 的共同经验一致：验证工具本身会失败，不能把 CSS fallback、异常截图或“页面有内容”当作实时 3D 通过。

## 对本机 3D Animation Agent 的直接影响

### 保留轻量时间线表示

C2 证明以下数据已经足够成为模型的制作接口：

```text
duration
explosion tracks: part → axis × amount
camera keyframes: time → radius/angle/height/target
label opacity windows
light envelopes
```

不需要先做通用场景 IR。若多轨阶段频繁串扰，可以把这些轻量 tracks/keyframes 写进 Skill 参考和工具读回，而不是增加多 Agent。

### 验收必须同时读三个空间

1. **世界空间：**零件位置、装配轴、间隙和相机状态。
2. **屏幕空间：**主体是否出画、标签是否压主体、连线是否指向正确零件、UI 是否遮挡。
3. **时间空间：**阶段边界前后位置/透明度/速度是否连续，seek 是否与正常播放到同一时刻一致。

### 最终 UI 也属于版本证据

0 和 12 秒能一致，不仅因为零件归位，还因为时间轴、阶段标签和灯光也回到对应状态。只比较 Three.js 对象不足以证明整页可循环。

## Case 5 的直接观察点

C2 的 `cameraKeys` 为局部修改提供了清晰入口，但“只反转 6–9 秒环绕方向”不能只随手改一个符号：

- t=6 和 t=9 的相机状态决定阶段边界连续性。
- 改完 6–9 后，9–12 返回路径很容易被连带改变。
- 如果为了反向而修改 t=9 角度，必须明确它是否属于允许变化的目标阶段边界，不能默认 9–12 也自然不变。
- 应保存修改前后两个版本，比较 1、4、11 秒的未修改阶段；不能只展示 7 秒的新镜头。
- 零件位移、灯光、标签透明度、总时长和 UI 应保持相同，最好有状态/截图双重比较。

因此 C5 是验证**局部源码修改和跨阶段不变量**的探针，不是简单让模型把 `theta` 乘以 -1。
