## 技术路线

### 1. 场景实现

可见采用 Three.js 0.180 + Vite，未使用视频、外部图片或模型：

- 主球：高细分球体、金属 PBR、固定种子的拉丝纹理。
- 三个圆环：不同半径、材质和 Euler 倾角，附带轻微周期摆动。
- 六颗小球：每个圆环两颗，保持相反相位。
- 摄影棚：本地 RoomEnvironment 反射、主灯/补光/条形灯、底座和接触阴影。
- 镜头：8 秒内完整环绕一周，高度也有周期变化。
- 灯光与环境：主灯位置、强度和环境反射旋转都参与同一周期。

这与本机“源码级 Three.js + 固定构建”路线一致，不需要通用场景 IR。

### 2. 单时钟模型

核心形式是：

```text
time = ((seconds % 8) + 8) % 8
phase = time / 8 * 2π
scene_state = sample(phase)
```

所有运动直接由 `sample(t)` 计算，不依赖上一帧的旋转、位置或随机数：

| 通道 | 周期实现 |
|---|---|
| 三组小球 | 每 8 秒分别运行 1、2、3 圈，同组两颗保持相反相位 |
| 主球 | 整数周期旋转叠加正弦倾角 |
| 圆环 | 小幅正弦微摆 |
| 镜头 | 连续环绕一周，高度为正弦周期 |
| 主灯 | 位置和强度为周期函数 |
| 环境反射 | 8 秒旋转一周 |

这种设计天然比“每帧累加 rotation += delta”更容易保证 A→B→A 和冷加载一致。纯视觉周期运动不需要 fixed timestep。

**需求解释上的细节：**实现是三条几何圆环，每条承载两颗具有独立相位/速度的小球，因此有六条独立运动轨迹，但只有三条不同的几何轨道。如果用户把“各自的闭合轨道”理解为六个不同形状/半径的轨道，需要另行确认；当前轨迹没有把这当作失败。

## 正常播放与 capture 是两条明确路径

### capture 模式

- `?t=秒数` 直接定位到指定时刻。
- `window.__seek(t)` 暂停并渲染指定帧。
- capture 模式不启动连续动画循环。
- t=8 被归一化为 0，因此首末截图也包含相同的时间轴/UI 状态。

### 正常模式

- 自动播放，由同一个 `sample(t)` 更新所有通道。
- 播放/暂停按钮、空格键和时间轴实际操作。
- 拖动前记录播放状态，拖动后恢复。
- 软件 WebGL 限帧，硬件浏览器不主动限帧。
- 后续修复为：暂停时由 seek/input/resize 事件渲染，不再持续重画静态帧。

这是本机 Harness 必须分别验收的两条路径：**capture 全绿不能代替正常 autoplay 和控件测试；正常播放测试也不能代替确定性 seek。**


## 关键失败与返修

| 问题 | 处理与证据 | 对本机的意义 |
|---|---|---|
| 字符串时间被错误归零 | 初版 `normalizeTime` 同时检查原始 value 和 numeric，导致 query 字符串无效；后改为只检查 numeric | `renderAt` 必须测试字符串、负数、NaN、Infinity 和 T 本身 |
| WebGL 初始化失败 | 多种 Chromium/驱动失败后，使用独立 Xvfb 获得 `WEBGL2_OK`，见 `:2555-2584` | 不用 CSS fallback 冒充 3D；浏览器环境是验证链的一部分 |
| 正常全页截图超时 | 连续软件渲染过慢，加入软件渲染检测和 12fps 限帧，见 `:2898-3024` | capture 与正常模式分离；性能降级不能改变逻辑时间契约 |
| 暂停后仍持续重画 | 点击多次超时，之后改为暂停时事件渲染，见 `:3240-3270` | 静止/暂停不应无意义占用 GPU；正常控件响应也要验收 |
| 底座偏下、控件遮挡 | 调整相机 target、距离和横屏控制布局；摄影棚改为弧形背景 | 首屏、缩略图和局部图都需要看图，不只验证循环 |
| PMREM 警告 | `sigmaRadians` 从 0.045 调到 0.035 | 保留并清理真实控制台警告，不只关注 error |
| 共享项目被其他 case 覆盖 | 建立独立工作目录，最终对比源码后保存版本，见 `:1320-1538`、`:3691-3701` | 一题一工作区；最终发布源码与已验证源码必须哈希一致 |

## 不能过度解读

1. **不是所有通道的完整无缝运动学验收。** 已补相机和主灯接缝附近位移，但小球数值导数未暴露，仍不等于所有物体速度/加速度全证明。
2. **不是实时性能验收。** 软件渲染被主动限到 12fps，且本机播放仍慢于墙钟；诊断 FPS 不能外推到真实 GPU。
3. **原轨迹的普通点击问题有历史意义，本机结果另行通过。** 原轨迹曾使用 `force:true`；本机 21 项中的实际操作没有使用 force，但不代表所有设备/浏览器都稳定。
4. **不是原始 Kimi 截图复核。** 原始截图仍未收到；本机已生成并查看实际截图，独立视觉证据来自本机。
5. **不是原版本 `6f165dd` 的逐字节核验。** ZIP 和本机重建一致，但 ZIP 的 JS 资产名与轨迹最终记录不同，网页版本卡也未访问。
6. **不是原通用验证器全警告清零。** 原轨迹仍有 page probe warning 和大 JS chunk 警告；本机自定义 21 项是另一套检查，不冒充原验证器结果。
7. **不是六条不同几何轨道。** 是三个圆环上的六个独立运动体，需求若要求六条不同轨线需另行确认。

## 对本机 3D Animation Agent 的直接影响

### 保留现有主路线

C1 直接支持当前的绝对时间 `renderAt(t)`、确定性 seek、真实 Chromium 和源码候选证据，不需要改成 fixed timestep 或通用时间线编辑器。

### 增加/固定以下验收序列

1. **关键时刻：**0、1/fps、2、4、6、T-1/fps、T；检查状态、截图和必要导数。
2. **确定性：**A→B→A、冷加载、不同到达路径、字符串/负数/非法时间输入。
3. **正常播放：**不带 capture 打开，确认实际 RAF 推进，播放/暂停/拖动/空格均实际操作。
4. **暂停行为：**暂停后时间与场景状态保持不变，静态画面不持续重画。
5. **恢复行为：**恢复后继续推进，拖动前播放状态正确恢复。
6. **多视口：**桌面、横屏缩略图和手机分别检查构图及控件遮挡。
7. **性能口径分开：**软件渲染只证明功能与像素，不写真实设备 FPS 结论。
