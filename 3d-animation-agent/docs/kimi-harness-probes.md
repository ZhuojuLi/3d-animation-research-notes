# Kimi Harness 拆解与 3D Web Animation 探针

> 公开整理版 · 2026-11-25。保留成文时点的记录；计划、文献结果和本地实测请分别理解。 环境路径已泛化，未收录的附件已标注；发布范围见 [整理说明](../../PROVENANCE.md)。

日期：2026-11-16

## 目的与边界

当前只做 **3D Web Animation** 一条纵线，暂不扩展到 2D、游戏、Blender 重流程、CAD/BenchCAD、3D 打印或模型蒸馏。先通过少量 Kimi 任务观察用户可见的 trace、源码、验证行为和产物，再决定自己的技术路线。

本文记录的是架构探针，不是对 Kimi 私有实现的反推，也不是 benchmark 分数。Kimi 部分依据用户提供的 Skill 架构说明；巴黎案例的单独整理见 [kimi-reference.md](kimi-reference.md)。

## 分层拆解

| 层 | 需要回答的问题 | 本机通用底座 |
|---|---|---|
| Skill 路由 | 是否识别 3D Web Animation，按需加载场景/时间/浏览器规范 | 有 SkillRegistry，需要领域 Skill |
| 工程执行 | 是否完成 Three.js 源码、固定依赖构建、离线打包 | 文件/进程宿主可复用 |
| 场景表达 | 参数化几何、材质、灯光、镜头和性能是否服务需求 | 需要 Three.js 领域能力 |
| 时间系统 | 是否由绝对时间统一驱动物体、镜头和材质，能否 seek | 原 3D 打印项目没有 |
| 浏览器证据 | 是否真实运行 WebGL，收集错误、关键帧、循环和交互证据 | 原项目只有软件几何 PNG，不算浏览器验证 |
| 返修与版本 | 是否看实际帧、改权威源码、重验并保留旧版本 | 候选/哈希/自审框架可复用 |
| 外层评测 | 是否有固定题、可重复运行、并排图和成本/行为轨迹 | agent-harness replay/metrics 可复用 |

核心判断：优先补“确定性时间 + 真实浏览器 + 时序返修”，不要先上多 Agent、通用场景 IR、视频导出或物理引擎。纯视觉动画优先绝对时间；有状态物理模拟才考虑 fixed timestep。

## Case 1：单时钟与无缝循环

```text
制作一个实时 3D Web 动画，不要用视频代替：深色摄影棚里，一个金属球和三个不同倾角的圆环组成动力雕塑，6 颗小球沿各自的闭合轨道运行，镜头缓慢环绕。

整个作品 8 秒无缝循环，开始和结束时所有物体、镜头、灯光状态一致，循环处不能停顿或跳变。提供播放、暂停和时间轴拖动，交付可运行网页和源码。
```

观察：统一时间源还是独立定时器；是否可确定性跳帧；中间帧是否真实变化；首尾是否一致；随机布局是否可复现。漂亮首屏不等于通过。

## Case 2：多轨时间编排与镜头

```text
制作一个 12 秒实时 3D 产品动画：一个由底座、外壳、扬声器单元、控制面板和旋钮组成的模块化桌面音箱。

0–3 秒镜头推近并亮灯；3–6 秒零件沿装配轴爆炸展开；6–9 秒镜头环绕且显示零件标签；9–12 秒标签淡出并重新装配。

要求阶段衔接连续、零件不穿插、标签不遮挡主体，提供播放、暂停和时间轴拖动。不要用预渲染视频代替实时 3D。
```

观察：物体/镜头/灯光/标签是否共享时间线；是否先形成分镜或运动规格；是否检查 1、4、7、11 秒；阶段边界是否连续；返修是否修改权威源码。

## Case 3：滚动驱动与可逆交互

```text
制作一个 3D 滚动叙事网页，不要用视频。页面分为三段：远景看到一颗线框行星；滚动时行星逐渐成为实体，镜头接近并穿过云层；最后到达地表并出现结尾文案。

动画完全由滚动进度驱动，向上滚动能精确反向恢复；快速来回滚动不能卡住或叠加多个动画。给桌面和手机布局，减少动态效果偏好下有可用的静态版本。交付源码和可运行网页。
```

观察：是否只有一个滚动进度驱动各通道；正向/反向/快速滚动是否一致；同一进度是否与到达路径无关；是否实测手机视口和减少动态效果降级。

## Case 4：程序几何、随机种子与性能

```text
制作一个实时 3D 发光晶体群动画。至少包含 2000 个参数化晶体，大小、颜色和相位有稳定差异；一个 10 秒循环的波浪从中心向外传播。

每次刷新后的布局必须完全一致；鼠标只控制观察方向，不影响循环时间。要求持续运行时对象、材质和显存资源不不断增加，普通笔记本上可以交互。交付源码、预览，并说明你实际做了哪些性能检查。
```

观察：instancing/共享资源、固定随机种子、热循环分配、renderer 资源计数是否稳定。无头软件 Chromium 的 FPS 不能外推为真实硬件性能。

## Case 5：二次局部修改与版本保持

先运行 Case 2，再在同一会话追加：

```text
在上一版基础上只修改一件事：把 6–9 秒的镜头环绕方向反转。

其他零件运动、爆炸间距、配色、标签、总时长、布局和交互全部保持不变。请保存为新版本，重新运行并对比修改前后的关键阶段；不要重做整个作品。
```

观察：局部源码修改还是整体重写；是否保留旧版本；是否重新运行和看图；1、4、11 秒等未修改阶段是否保持不变，只有目标镜头阶段改变。

## 路线判读

- C1/C2/C5 能通过清晰源码和浏览器证据做好：采用薄 Harness + 源码级 Three.js + 浏览器验证，不做通用场景 IR。
- C2 证明轻量 `explosionAt(t)`、相机关键帧和标签/灯光包络已足够表达多轨产品动画；验收需同时覆盖世界空间、屏幕空间和时间空间，seek 后先更新矩阵再投影。
- C1 进一步确认绝对时间与整数周期函数适合纯视觉循环；除 0/T 像素一致外，还要测接缝附近连续性、正常播放时钟速率和普通点击，不能把软件限帧或 force click 当作完全通过。
- C3 支持独立的 `renderProgress(p)` 契约、原生滚动与按需渲染；快速直接 seek 和真实 wheel/touch 必须分别验证，滚动控制的 DOM/CSS 也不能暗藏墙钟过渡。
- C4 支持“静态实例参数 + GPU 纯时间着色器 + 固定资源 + 正常播放 soak”；性能证据必须同时给帧数/墙钟均值、EMA、资源计数和质量档位，静态/暂停时不能显示伪 60 FPS，OrbitControls 复位还要检查阻尼残量。
- 反复出现初始化、依赖或构建问题：增加薄模板，不扩大 Agent 架构。
- 多轨阶段和局部修改频繁串扰：只增加轻量 tracks/events/easing/duration 时间线表示。
- 有碰撞、状态累积或帧率相关模拟：才引入 fixed timestep。
- 黑屏、404、无法跳帧、无真实截图：先修浏览器工具链，不靠提示词或多 Agent 掩盖。
