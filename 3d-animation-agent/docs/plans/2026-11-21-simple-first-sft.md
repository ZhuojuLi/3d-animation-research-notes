# 朴素首版 SFT：万级代码数据 + Agent 轨迹增量计划（草案）

> 公开整理版 · 2026-11-25。保留成文时点的记录；计划、文献结果和本地实测请分别理解。 环境路径已泛化，未收录的附件已标注；发布范围见 [整理说明](../../../PROVENANCE.md)。

2026-11-21

本草案响应用户最新方向：减少前期准备，先把原生 baseline 跑好，并尽快形成有实际规模的训练与测试素材。它不修改共享 `decisions.md`。首版先训练一个学生，不做复杂消融。

**规模修正：36 条只能做探针，不能承担 27B 的领域 SFT。首版采用“万级现有代码数据打底 + 数百条新 Agent 轨迹”，而不是新造一万个完整 Agent case。**

answer-only 本地路径：`${REFERENCE_DATA}/code2video/training/data/threejs-mixed-swift-answer-only-v1/`。它已经过 Swift loader 回读和模板/掩码检查，来源为 CCORE Scenes、Scenes-v2 和 GLB Assets，保留原有 train/validation 划分。记录数不等于独立程序数，仍需保留来源 ID、去重和近重复边界。

首版默认使用 answer-only，避免把长思考和复杂权重矩阵带入第一轮。带思考 Ready v2 只保留为后续对照。

## 首版只保留一条训练线

- 起点：同一个原版 BF16 `${MODEL_ROOT}/Qwen3.8-27B`。
- 学生：一个混合数据 SFT，而不是同时训练多个消融组。
- 数据组成：万级单轮代码生成记录 + 新采集的多轮 Agent 行为轨迹。
- 代码记录：学习用户要求到完整源码。
- Agent 记录：学习验收通过轨迹中的 assistant 正文和工具调用，system/user/tool result 作为输入。
- 原始 thinking 完整归档，首版不作为监督目标；不改写思维链，不做短说明消融。
- 实际图片保留在可见轮次，沿用已通过的 Swift `<image>` + `images` 路径。
- 不做 one-shot 学生、DPO、RL、专用 Harness 或思考权重矩阵。
- 不用失败轨迹凑正样本，不靠同题重复采样或增加 epoch 掩盖数据不足。

## 新增 Agent 素材规模

第一阶段以 **200 个新 Agent case 为采集目标**，后续根据合格率扩到 500；不是只造 24 个。

| 类型 | 第一阶段目标 | 主要来源 |
|---|---:|---|
| 生成 | 60 | WorldCoder、OCTAVE、VibeVideoBench 提炼的新任务 |
| 修复 | 80 | 优先从 CCORE 合格源码做单缺陷派生 |
| 局部编辑 | 60 | 优先从 CCORE 合格源码派生并检查非目标保持 |
| 合计 | 200 | 与现有种子按场景家族去重 |

- 200 个完整 case 通常能展开为数千个有监督的 assistant 决策回合，但不能把回合数冒充为独立 case 数。
- 目标是约 150 条以上通过验收的教师轨迹，再逐步扩到 500 case；实际入选由质量决定，不强行凑数。
- 新 train 题只跑 Kimi，不再让 Qwen 陪跑所有造数题。
- 现有 12 个种子只有补过目标语义复核和连续画面验收的部分才能进入 train；被排除的题用新 CCORE 题补。

## 独立 dev/test

- Agent dev：6 个新题簇，每类 2 题，用于配置和 checkpoint 选择。
- Agent test：12 个新题簇，每类 4 题，用于最终主要对照。
- 代码生成验证：保留现有 answer-only 的 812 条 validation，不与新 Agent dev/test 混为一谈。
- train/dev/test 先按原场景、素材和任务模板家族划分，再派生故障或编辑。
- GameASG 保留作游戏/交互外测；Animation2Code 的官方 test 没有 Three.js，不承担当前测试集。

## 每题的最薄质量门禁

每题只保留 1–3 个能区分任务成败的关键断言：

1. 最终离线 HTML 可运行，`renderAt(t)` 可重复。
2. 目标动作/编辑确实发生，不能只检查“物体存在”或“正在动”。
3. 修复/编辑题检查关键非目标状态保持。
4. 修复题必须有已知好版和单缺陷版；当前断言至少能拒绝坏版。
5. 保存实际关键帧；开放视觉质量用连续片段人工复核。

发现 fixture 或断言问题时修题，不把它记成模型失败。质量失败的教师轨迹不反复采样择优。

## 并行执行顺序

### A. 原生 baseline

冻结现有 256K、medium、通用 Claude Code 工具和 3600 秒上限。先跑 6 个 Agent dev，再跑 12 个 Agent test；每题一次，只有基础设施错误允许原样补跑一次。保存交付、原始轨迹、浏览器证据、时间和 tokens。

### B. 训练素材

先生成 200 个 train 题包，按 2 并发跑 Kimi，每 40 题收割一次，避免最后才发现系统性问题。同步复核现有 12 个种子。最终统一导出为 OpenAI/exchange/Ready，记录任务族、教师模型、输入图片、loss mask 和来源哈希。

### C. 捕获补洞

请求捕获补齐与题包生产并行，不再阻塞素材调查。正式 SFT 前，用新捕获跑一条文本和一条双图 canary；正式轨迹必须能保存实际 system、工具 schemas、压缩后的消息和图片到达记录。

## 训练与最终评价

正式训练使用团队固定 Swift/Megatron 镜像，先做目标训练配置的小步 smoke。首版只做一次混合 SFT，按来源分别报告数据量和 token 占比；如果 Agent 行为被万级代码样本淹没，后续再调比例，不在首版预设复杂加权实验。

最终在冻结 Agent test 上比较原生 27B 与学生：

- 正式交付率和全部必要断言通过率。
- 修复/编辑的目标成功率与非目标保持率。
- 连续视频盲评。
- 每次成功的耗时和 token，以及超时率。

Kimi 可在同一 test 上补跑作参照，但不是 baseline 启动的前置条件。首版回答的是：**万级代码数据提供领域底座后，新增 Agent 行为轨迹能否进一步改善独立题簇上的交付与返修。**
