## 一句话结论

这是目前第一份返回的完整可见执行轨迹，对应 **Case 3，而不是 Case 1**。它强烈支持“**原生滚动 + 单一归一化进度 + 纯函数场景更新 + 按需渲染**”这条路线；不需要为了滚动叙事引入 fixed timestep、GSAP 时间线、通用场景 IR 或多 Agent。

它也暴露了两个必须吸收的工程问题：

1. **路径无关性不只要检查 Three.js 状态，还要检查 DOM/CSS。** 一处 `180ms` 导航过渡就使同一进度在首次比较中无法逐像素恢复。
2. **`__seek(p)` 的快速跳转测试不能替代真实 wheel/touch 连续输入。** 本例验证了纯函数和状态恢复，但还没有完整证明真实快速滚动体验。

### 2. 发生了真实的跨任务工作区污染

第一次构建报错：`createPlanetaryScene` 没有导出。继续读取后发现，当前滚动案例的 `scene.js` 已变成模块化音箱代码，目录出现 `speaker.js`，HTML 标题变成 `MODUL 01`。

证据：`../references/kimi-probes/case-03-scroll/transcript.txt:925-1137`。

这说明至少在该执行环境中，并发任务曾共用 `/mnt/agents/output/app` 并相互覆盖。**这些音箱片段是污染证据，不应误归为本滚动案例的功能，也不能当作完整 Case 2 轨迹。**

Kimi 随后新建 `/mnt/agents/orbit-app` 作为隔离 staging，重建源码，完成验证后再同步到交付目录。这是有效的自救，但更合理的 Harness 设计是从一开始就一题一工作区，而不是等冲突后恢复。

### 3. 场景不是视频，也不是静态海报冒充实时 3D

可见源码使用 Three.js 0.180.0 和 Vite，主要组成是：

- 行星：球体几何 + GLSL 程序地形、海洋/陆地、光照、雾化和边缘光。
- 线框：经纬线 `LineSegments`，不是简单打开三角面 wireframe。
- 星空：固定随机种子的 `Points`。
- 云层：噪声云壳、点精灵和 DOM 云雾遮罩，不是体积云模拟。
- 地表：同一行星球面、实例化山体和碎石、天空穹顶与雾，不是另加载视频或第二张背景图。
- 镜头：位置、目标和 up 向量的进度关键帧，在太空中看向球心，落地时逐渐转为沿地表看地平线。

静态阅读海报也从同一 3D 场景的三个固定进度生成；CSS 图形只作为 WebGL 不可用时的降级。这与“用静态截图伪装实时场景”是不同路径，验证时必须检查动态模式确实存在 WebGL canvas。

## 核心架构：进度是纯函数输入，不是另一个时钟

### 进度模型

轨迹中的 `src/main.js` 将页面滚动归一化为：

```text
p = clamp(scrollY / (documentHeight - viewportHeight), 0, 1)
```

场景、镜头、材质、文案、导航和进度条都读取这个 `p`。滚动事件只保留一个 pending `requestAnimationFrame`，回调读取**最新**滚动位置；没有独立播放循环，也不通过 lerp 追赶目标进度。

关键性质：

- `applyScene(p)` 不读取上一帧状态。
- 正向、反向和跳跃都走同一函数。
- 连续滚动事件可合并，但不会排成多个动画队列。
- 原生滚动没有被 scroll-jacking；章节导航使用即时 `scrollTo`。
- 场景渲染和 DOM 界面更新分开，静态海报捕获不会意外驱动整套 UI。

证据：`../references/kimi-probes/case-03-scroll/transcript.txt:893`。

### 对我们的契约启示

本例的 `window.__seek(0.64)` 和 `?t=0.64` 实际表示**归一化进度**，不是秒。我们不应原样照搬这个命名。

建议未来在本机 Harness 中明确区分：

```text
时间动画：renderAt(seconds)
滚动动画：renderProgress(progress01)
```

浏览器检查器也应分别报告 `time_seconds` 和 `scroll_progress`，不要让 `t` 同时承担两种单位。滚动案例不需要固定步长；只有碰撞、状态累积等模拟才另行考虑。

## 静态与响应式不是附属说明，而是实际实现路径

### 减少动态效果

- `prefers-reduced-motion: reduce` 初始进入静态阅读。
- 静态模式展示三张由同一场景生成的 1200×750 海报和完整三段文案。
- 固定 WebGL 场景在静态模式中隐藏，没有持续动画循环。
- 右上角可以手动切换静态/滚动模式。
- WebGL 创建失败时，CSS 图文降级仍能阅读。
- HTML 还包含 noscript 降级，但本轨迹没有独立验证禁用 JavaScript 的全部表现。

### 桌面和手机

实测视口为桌面 1440×900、手机 390×844。手机不是简单缩小桌面，而是调整 FOV、取景目标和文案位置。看手机首屏后发现行星裁切，随后将移动 FOV 从 51 调到 56，并改变初始 target；这证明响应式修复来自实际图像，而不只是 CSS 媒体查询存在。

## 不能过度解读的部分

1. **原轨迹不是完整真实快速滚动测试；本机已补基本输入验证。** 原轨迹的 20 次序列直接调用 `__seek`，本机另测 10 次真实 wheel 和 6 次 touch 手势，均保持场景与实际 scrollY 一致、pending RAF 峰值为 1；仍不是长时间性能测试。
2. **仍不是完整跨浏览器验收。** 原轨迹最终使用 Firefox，本机独立使用 Chromium/SwiftShader；真实 GPU、Safari 和更多浏览器未测。
3. **不是独立审美通过。** 本机已生成并查看实际截图，且发现 p=0.68 标题裁切和云层文字对比度问题；不能因机械检查多数通过就评为视觉全通过。
4. **不是全帧证明。** 六个桌面进度和三个手机进度仍可能漏掉其他中间状态。
5. **不是性能基准。** 没有真实设备 FPS、长任务或资源增长测试；draw calls 和三角形数只能说明量级。
6. **ZIP 已核验，原始版本卡未访问。** 本机重建 `dist/` 与 ZIP 逐字节一致，但这不证明原始网页服务仍在线。
7. **不需要因此引入重型滚动库。** 本例的核心可靠性来自纯进度函数和移除额外时间状态，而不是更多依赖。

## 对本机 3D Animation Agent 的直接影响

当前本机浏览器脚本只有单视口时间动画检查，没有滚动、减少动态效果或 touch/wheel 工具。这份案例支持按以下顺序补最小能力：

### P0：建立滚动模式的独立契约

- 新增明确的 `renderProgress(p)` / 进度捕获协议，不强迫任务把时间动画改成滚动。
- 检查正常原生滚动路径与专用 seek 路径，二者不能相互替代。
- 将 canvas、WebGL 上下文、page error 和外部请求作为硬门槛；CSS fallback 不计为实时 3D 成功。

### P1：补交互和视口证据

- p→q→p、冷加载、直接 seek、真实 `scrollTo`、wheel/touch 快速往返分别验证。
- 检查同一进度截图、关键场景状态和 DOM 状态；截图等待条件必须明确，不能靠任意 sleep 掩盖过渡。
- **对 opacity > 0.5 的标题记录 bounding rect，必须完整位于视口内；sticky 场景还要检查容器剩余高度。** C3 的 0.68 裁切证明 opacity 正常仍可能视觉失败。
- 至少桌面/手机两个视口；按任务检查 `prefers-reduced-motion` 和静态文案可读性。
- 在云层、爆炸、特效峰值等任务关键时刻采样，不固定只取首末帧。

### P1：防止评测工作区串改

- 保持一题一 workspace、独立候选和源码哈希。
- 归档多个 Kimi cases 时，明确标记其他任务混入的片段，不把污染文本当作本案例功能。
- 最终发布必须由当前候选生成，不能信任共享输出目录里“最后剩下的文件”。

### 暂不增加

- 不做通用滚动场景 IR。
- 不为了此案例引入 fixed timestep 或物理引擎。
- 不把 `window.__seek` 命名和 `?t=` 的进度/秒混用带进本机契约。
- 不把“静态海报由 3D 生成”误算为动态 WebGL 验证通过。
