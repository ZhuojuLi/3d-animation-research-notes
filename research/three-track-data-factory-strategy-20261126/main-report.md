## 二、如何“既吃满红利、又不踩漂移坑”地吸收小红书 `3DCodeFactory`？

今天刚跑完的 `9B-Ctrl` vs `9B-3DCF-Mix` 受控消融给出了极宝贵的实锤警告：直接把 33% 小红书原始 Three.js 轨迹（含 94% 无 EOS prefix 切片、`importmap` + `http.server` 多文件）混灌进训练集，虽然 `eval_loss` 更低、数学准确率升至 `76.2%`，却把离线单文件内联率从 **`66.7%` 打回 `23.1%`**、硬检查打回 **`0%`**、超时率从 `23.3%` 翻倍至 **`38.5%`**。

因此，吸收小红书必须拆成 **4 个严格分级的层级（L1–L4）**，而不是笼统说“把数据加进来”：

### L1 · 方法论与基础设施 100% 吸收（零风险、三轨通用）
把小红书 `P01–P11` 抽象为我方统一的 **`Visual-CodeFactory Core`（三轨共用框架）**：
1. **分类树 + 双向分布对齐（`P01`）**：多源去偏、扁平多标签复合场景、高频降采样 + 长尾保底配额 $n_{\min}$ 回捞；
2. **前置 `P07` 零隐藏考纲审计**：每条 Rubric 考点必须 100% 明文写进 `task_prompt`，根治 `print-gear-spur-build`（缺 `Z=0` 基准）与 `cycloidarch`（缺 `__3D_STATE__` 字段名）类误杀；
3. **五维合取门控 + Best-of-2 + 难度校准**：任一维 `<0.50` 淘汰、均分 `<0.60` 淘汰、同题收 2 条合格取高分；对高难度几何做先验偏置校准；
4. **`trajectory.py` 5 规则轮级异常 Loss Masking（“掩坏轮、保纠错轮”）**：已在 `logging_proxy_to_swift.py` 落地，三轨强制启用；
5. **100% 保留 DeepSeek 原生简短 `<think>`**：停止所有 Markdown 方案书腔 CoT 改写；
6. **1 Epoch 原则 + 极低单轮占比**：把单轮压回 `≤10%`（避免 Round 2 `65.8% × 2ep` 训成首轮空想 6.7 万字符的长思考写手）。

### L2 · 零成本高价值资产 100% 吸收：题面 + 视觉参考图种子矿（省下巨额文生图与出题费）
- 本机 `${WORKSPACE}/datasets/3dcodefactory/` 已校验留存 **`217 / 401` 分片（167.52 GB，0 损坏）**，包含 ~1,100+ 道独立 Three.js 场景的**去污染中英双语需求 + 高精视觉参考图 `reference-0.png`**（外推全库 401 分片约 2,125 道）。
- **正确吃法**：把这些已通过小红书 56 叶分布对齐与 4 大榜单去污染的高审美场景（建筑/室内/自然/科学展陈/机械装置），直接喂进**我方同栈新管线**（`threejs_rubric_synth.py`（本地附件未发布） + `run_threejs_best_of_2.py`（本地附件未发布）），注入“确定性连续 3D 运动（`window.renderAt`）+ 离线单文件 `esbuild` 内联 + 2–3 轮拼图硬停（35–55 轮、≤131K）”，用约小红书 **1/6 的单题 token 成本** 产出 100% 同栈、高审美、完整 EOS 的 3D 动画轨迹！

### L3 · 原始小红书 Three.js 完整轨迹的“条件式吸收”（先消融再放量）
小红书每条 Three.js 轨迹烧了极高成本做材质、光影和 `PIL.crop` 局部特写精修，扔掉全部很可惜，但**必须先排除导致 `9B-3DCF-Mix` 翻车的两大毒源**后才能复用：
1. **硬门禁 1：只留完整收尾（Full EOS）段，0% 无尾 Prefix 切片**（`9B-3DCF-Mix` 翻车元凶之一是 94% 为无 EOS 截断切片，直接教坏模型不收尾）；
2. **硬门禁 2：显式双契约模式隔离（Mode Tagging）**：
   - 保留小红书原始多文件形态时，必须在其 `system` / `task_prompt` 显式标明 **`[Mode: Multi-File Interactive WebGL Scene (local http.server + vendor)]`**，与我方 **`[Mode: Standalone Offline 3D Animation (esbuild single-file + window.renderAt)]`** 明确隔离；
   - **可选升级（高杠杆实验）**：探索用确定性脚本对小红书 Three.js 最终产物做 `esbuild` 单文件打包，或在末尾追加 1 轮“打包离线化验收”？**（风险：人为拼接尾轮可能引入 off-policy 断层，须作为备选请 Astra 审慎评估，默认不拼接而是显式契约隔离 + 低比例混入）**。
3. **小比例验证门控**：在 27B（或先在 9B 复验“去 prefix 切片 + 显式模式头”）上只测试 **`10%–15%`** 完整 EOS 小红书 Three.js 轨迹，验收标准是 **`devtest-v2` 离线内联率与硬检查不降、同时 `visual_craft` 美学分显著提升（≥ +0.3/5.0）** 才放行，否则只吃 L1+L2。

### L4 · Blender 轨迹明确隔离（当前 0% 混入）
- 除非团队正式批准新增“Blender 艺术建模/离线渲染”第 4 子轨，否则 2,920 条 `bpy` 轨迹保持 `0%` 混入，避免重复论文 Table 2 证实的 Three.js 负迁移。

## 三、三棵数据分类树全景设计（3D 动画树 + CAD 建模打印树 + 2D 动画树）

严格遵循小红书“**两级主域-叶节点树 + 扁平多标签复合 + 双向配额对齐 + 非互斥路由预标注 + 难度分层**”的设计范式，同时把**27B 实测能力边界**写进树的结构里。

### 树 1：3D 动画分类树（复用裁剪小红书 56 叶 × 连续物理动画机理轴）

直接裁剪小红书 56 叶作为“题材/空间轴”（重点保留建筑、室内外、设备机械、载具、自然天体、家居、文娱装置，降权/剔除高有机人体角色 `D09L01`），与我方独有的 **6 大连续运动机理轴** 正交配对：
- `M01` 刚体机械传动（齿轮系/连杆/凸轮/擒纵/钟表/曲柄滑块）
- `M02` 物理力学与弹性碰撞（摆/弹簧/多米诺/抛体/碰撞恢复/共振）
- `M03` 光学、波动与电磁场（棱镜色散/驻波干涉/反射折射/磁力线与粒子运动）
- `M04` 流体、粒子与自然气象（溪流瀑布/雨雪烟雾/火焰/风吹植被/水波涟漪）
- `M05` 天体轨道与算法几何演化（行星太阳系/分形/数论几何/网格变形/构造过程）
- `M06` 展陈空间交互与部件开合（门窗/抽屉/机柜/光影昼夜/多机位巡检——**直接承接小红书 Three.js 强项**）

> **任务形态配比（全轨防过拟合纪律）**：`build / high-craft generation 35%` + `real defect_repair 35%` + `local_edit 20%` + `healthy_control 10%`。

### 树 3：2D 动画分类树（`Anim2D-Tree v1`：8 大主题域 × 36 个细粒度叶节点）

**设计锚点**：
- 2D 动画与我方 Three.js 离线单文件动画共享几乎同一套浏览器验证框架（Playwright + Headless Chromium + `window.renderAt(t)` + `#play/#pause/#scrub` + `willReadFrequently: true` 逐字节确定性），但单条轨迹更轻（预计 15K–45K tok）、渲染更快、视觉审美与物理/教学表现力极易直观验收。

## 四、三轨统一推进节奏与合训配方（分阶段、防串扰、控预算）

### 4.1 为什么绝不能“一开始就把三轨全塞进同一个 SFT 锅里硬炒”？
1. **当前最大现实约束**：`.env.deepseek` 额度当前耗尽（需补换配额），且三轨成熟度差异极大——3D 动画已有 `devtest-v2`（60 题）+ `Eval v3` + Astra 联检后的新管线；CAD 刚跑完 12 题 Phase 0（需先修 4 项 P0 + 补 OOD 尺子）；2D 尚未跑过一次 27B Base 基线！
2. **长度鸿沟风险**：Three.js 单条 `60K–150K` tok、2D 单条 `15K–45K` tok、CadQuery 单条 `9K–28K` tok。如果盲目按条数混配，1 条 Three.js 的监督 token 相当于 5–8 条 CadQuery，短轨会被淹没或过拟合；必须用**五本账（按有效监督 token `U` 与加权和 `W`）**精确配平。

## 五、本提案主动暴露的 5 个关键待审分歧点（供 Astra 重点挑战）

1. **L3 原始小红书 Three.js 完整轨迹到底该不该直接入训？** 是“只吃 L1 方法论 + L2 种子矿（彻底 0% 原始多文件）”更干净，还是“显式双模式契约隔离后混入 10%–15% 完整 EOS”收益更大？
2. **三轨合训中的“长短序列梯度失衡”**：Three.js（~100K tok）与 CadQuery（~18K tok）长度差 5×–8×，按有效监督 token `U` 给 CAD 18% 需要 ~700–1,000 条轨迹（或上采样），这会不会导致 CAD 过拟合？还是应该采用 **“同权重分轨打包 + 两阶段/多卡并行”** 或 **控制 3D 单条上限在 ≤90K**？
3. **CAD 与 2D 的 36 叶分类树颗粒度与 27B 边界**：36 叶是否太细（导致早期 500 条每叶平均不到 15 条，难以凑齐配对）还是太粗？有没有漏掉关键高频类或混进了 27B 做不稳的陷阱类（如 2D 角色行走循环 `A07L01`、CAD `L/T 型 Sweep 弯头 C06L03`、双件齿轮齿条配合 `C03L02`）？
4. **2D 动画是否需要像小红书那样走文生图参考图 $I$？** 静态单帧参考图能否锚定“动态 2D 动画”的运动规律，还是会误导模型只画静态插画、忽略物理/时序连贯性？
5. **“3D 建模打印”是否要彻底排除 Blender？** 如果未来用户说“给我建个手办/摆件打印出来”，CadQuery 是死穴，要不要现在就把“功能结构件（CadQuery）”与“外观模型（图生 3D / Blender）”的边界写进产品口径？
