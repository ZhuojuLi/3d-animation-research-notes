你这次纠正后，我会把上一版方案中的三点明确改掉：

1. **不再把 ReAct 轨迹压缩成“题目→最终代码”作为主要蒸馏形式**，而应保留完整的动作、执行结果、截图、状态检查和返修过程。
2. **不再把单轮代码 RL 作为主要 RL 形式**，而应优化完整的“生成—执行—观察—修改—复验—交付” episode。
3. **不在第一阶段加入轮数、token 或时间惩罚**，避免模型学会少检查、早交付。质量优先时，成本只记录，不作为主要优化目标。

## 一、重新对齐后的任务定义

我现在理解你的目标是：

```text
一个 Agent episode：
理解需求
→ 编写完整代码或修改代码
→ 由沙盒执行
→ 返回日志、数值状态、截图和交互结果
→ 模型理解新证据
→ 决定继续修改、换机位、裁剪、拖动、运行检查或停止
→ 多轮迭代
→ 正式交付高质量成果
```

模型本身不直接执行程序，但**模型可以在多轮响应中主动发起工具调用**，由环境执行后再把结果喂回来。

因此，你们的 `Accepted@1` 应理解为：

> **一次完整、独立、无人工接管的 Agent 运行最终通过验收。**

这里的 `@1` 不是一次模型响应，也不是 one-shot 代码生成。

而且，多轮工具本身并不会自动带来收益。RLEF 的实验很有启发：未经过对应训练的模型，拿到错误代码和执行反馈后，多轮修改未必比独立重新采样更好；经过执行反馈训练后，模型才更明显地表现出利用反馈进行修复的能力。

所以你们要训练的不是“调用工具的形式”，而是四种真正能力：

- 根据证据定位问题；
- 选择下一步最有信息量的检查；
- 把日志、状态和画面转化为正确修改；
- 修改后重新验证，并有依据地停止。

## 二、调研后最重要的结论：学生中心蒸馏应放在核心位置

你们当前“万级代码底座＋少量教师 ReAct”的主要问题，不只是 ReAct 数量少，而是**状态分布不匹配**。

教师轨迹通常覆盖的是：

```text
教师写出基本正确的代码
→ 得到基本正常的画面
→ 做少量抛光
→ 成功交付
```

学生实际遇到的却是：

```text
学生写错相机或机构
→ 看到遮挡、穿插、残影和错误运动
→ 已经进行过一次失败修改
→ 工作区和上下文都处于教师成功轨迹没有覆盖的状态
```

这就是序贯决策里的 covariate shift：训练时看的是教师会走到的状态，部署时面对的却是学生自己造成的局面。学生越早出错，后续状态就越偏离训练数据，误差会不断累积。

DAgger 在现代多轮 Agent 上的重新研究，正是通过学生与教师交替执行，让学生在真实交互中走到部署时可能遇到的状态，再由教师提供监督，缓解这种分布偏移。

因此，我现在的优先级建议是：

```text
教师完整轨迹冷启动
→ 当前学生真实交互
→ 定位首个关键错误
→ 从错误前快照恢复
→ 教师只纠正关键动作
→ 学生继续完成后续任务
→ 独立验收最终成果
→ 用这些学生状态上的教师纠偏训练下一版
```

这比单纯继续增加“教师从头成功做到尾”的轨迹，更适合你们当前阶段。

## 三、具体应该怎样采集下一代数据

### 1. 教师完整轨迹仍然保留，用于冷启动

原来的 249 条 ReAct 不应丢弃。Aodi 单轮代码数据也仍然可以承担代码底座和能力保持作用，但不再是 Agent 能力的主体。

完整轨迹中应保留：

- 真实 system、工具 schema 和初始文件；
- 每轮 assistant 的推理、工具名、参数和代码；
- 编译日志、浏览器错误和数值检查；
- 原始截图、局部裁剪和多视角图片；
- 时间轴拖动、暂停、恢复和交互结果；
- 每次编辑后的代码版本与证据版本对应关系；
- 最终交付和独立验收结果。

训练时通常只监督 assistant 产生的推理、动作和代码，**环境返回的文本、日志和图像观察不作为生成目标**。工具决策、工具参数控制和长代码内容也应分开统计损失，不要继续用一个“工具调用权重＝2”笼统覆盖所有内容。

### 2. 成功轨迹也不能默认每个动作都值得模仿

“最终成功”不代表中间没有低效或错误动作。建议给每个 assistant turn 增加动作级标签：

```text
productive：有效推进任务
recovery：从错误或坏状态中恢复
neutral：可接受但非必要
invalid：格式错误、无效命令
stale：使用旧截图或旧证据判断新版本
regressive：引入回归或破坏非目标状态
premature：证据不足就交付
```

对于 `invalid`、无意义重复和明显错误绕行，可以屏蔽其 SFT 正例损失；但其后续真实恢复过程应保留。长上下文多轮 SWE Agent 的训练也采用了先筛选成功轨迹、再屏蔽环境格式错误 turn 的 RFT 做法，而不是把所有 assistant turn 不加区分地当作好行为。

### 3. 重点生产“学生出错后的教师纠偏”

SCoRe 的思路与你们的需求尤其接近：学生生成轨迹，教师在首个关键错误处介入，形成与学生能力匹配的数据；之后还可以从验证过的前缀开始短程 RL。

你们可以这样落地：

```text
学生执行到第 t 步
→ 保存完整快照
→ 学生继续失败、循环或交付不合格
→ 教师结合后续证据，定位首个关键错误
→ 恢复第 t 步之前的快照
→ 教师只给出第 t 步的正确动作或一小段恢复动作
→ 学生从该状态继续
→ 必要时再次介入
→ 最终独立验收
```

这里有两个要点：

- **教师不是从头重做一遍**，而是在学生真实状态上示范“下一步该怎么走”；
- “首个关键错误”不一定是第一个编译错误，也可能是更早的错误决策，例如该看真实画面时盲改、该检查时间一致性时只检查静帧。

学生的错误动作可以留作偏好负例；教师的纠偏动作作为 SFT 正例。这样同一批数据既能做 correction SFT，也能做分支 DPO。

### 4. 沙盒必须支持快照和分支

这是很重要的工程前提。每个关键节点最好能够保存：

- 文件系统与代码版本；
- 浏览器页面和场景状态；
- 当前相机、时间轴和交互状态；
- 完整消息历史及图片引用；
- 当前证据哈希；
- 模型、解码参数和工具版本。

有了快照，才能从同一个学生前缀分出多条后续轨迹：

```text
同一个出错前状态
├─ 学生原动作 → 后续失败
├─ 教师纠偏动作 → 后续成功
└─ 学生的其他动作 → 部分指标改善／恶化
```

这比“完整教师轨迹与完整学生轨迹做比较”更接近局部信用归因，也更节省搜索成本。

## 四、视觉返修必须作为一等训练信号

你的判断是对的：复杂 3D 不能只靠编译和数值断言。很多错误只有真正换机位、裁剪、拖动和观察后才能发现。

3D 场景领域也已有类似方向。SceneAssistant 在每轮操作后向 VLM 返回新的渲染图，让它根据视觉反馈继续调整场景，而不是一次性生成全部内容。

但训练数据要特别强调**视觉观察与后续修改之间的因果关系**：

```text
当前版本截图／裁剪／另一机位
→ 模型指出具体可见问题
→ 修改对应的相机、几何、材质或时间代码
→ 重新构建
→ 查看当前版本的新图
→ 问题消失或确认仍未解决
```

不要把截图替换为一句文本摘要，也不要只训练“截图→口头评价”。最终要学的是“截图→有效动作”。

建议单独建立以下视觉缺陷任务：

- 主体出画、过小、被遮挡；
- 关键动作发生但未被镜头拍到；
- 几何穿插和接触关系视觉不一致；
- 材质、颜色、光照导致对象不可区分；
- 回拖残影、循环接缝和暂停恢复异常；
- 初始场景健康，检查后不应乱改；
- 修改目标对象时，非目标机位和对象应保持。

同时不要把 VLM 裁判神化。CADCodeVerify 展示了生成验证问题、观察多视角图片并迭代修改 CAD 代码的价值，但其人工抽查中，视觉问答准确率在两个 refinement 阶段也只有 64.6％ 和 68.2％。

所以你们应当采用：

- 数值状态与几何检查作为硬信号；
- VLM 帮助发现开放性视觉问题和提出返修建议；
- 后续新图和独立验收证明返修是否有效；
- 视觉裁判不确定的样本允许 `unknown`，不要硬转成训练奖励。

## 五、多轮 RL 应该怎样接入

### 第一阶段：先做完整 episode 的结果奖励基线

在 correction SFT 已经让学生具备一定修复能力后，可以采样多条完整 Agent 轨迹：

```text
同一道题
→ 当前学生独立运行 K 个完整 episode
→ 每条允许多轮工具、观察和修改
→ 最终用独立验收计算奖励
→ 优化所有 assistant 动作，屏蔽环境观察的生成损失
```

长上下文、多轮 SWE Agent 已验证了“成功轨迹 RFT 冷启动＋多轮 RL”的路线，并报告从 20％ RFT 基线提升到 39％，说明这种方法并不限于单轮代码。

但这只能作为参考，不能照抄其稀疏奖励和长度惩罚。你们的视觉质量、交付正确性和非目标保持都比普通单元测试复杂。

### 第二阶段：用共享前缀和短程 RL 改善信用归因

完整轨迹最终失败，可能源于很早以前的一次错误观察或修改。把同一个终局优势平均分给所有动作，信用非常粗糙。

更适合你们的是：

```text
从验证过的学生前缀恢复
→ 采样几种下一步动作及短期后续
→ 比较哪个分支真正提高后续验收
→ 给关键决策更局部的训练信号
```

这可以先用分支 DPO，再做短程 RL，不必一开始就引入复杂的 turn-level value model 或 Agent Lightning 式信用分配系统。

### 奖励设计要坚持“结果质量优先”

主奖励应是最终独立验收，过程信号只作为辅助：

- 离线冷加载和正式交付；
- 必要动画语义与几何约束；
- 真实视觉可读性；
- 修复和局部编辑的非目标保持；
- 当前版本证据与交付版本一致。

可以给“首次可运行”“关键缺陷已消除”“独立语义检查新增通过”等**真实状态改善**有限的里程碑奖励，但不要奖励：

- 调用了多少次工具；
- 看了多少张截图；
- 写了多少条自检；
- 自称检查通过；
- 单纯减少轮数；
- 单纯减少编译错误数量。

否则模型很容易学会“为了得过程分而检查”，或者“为了避免惩罚而不检查”。

在质量优先阶段，也不应给所有额外步骤统一负奖励。真正需要惩罚的是无意义循环、使用陈旧证据、重复无效修改和未经验证提前交付，而不是认真复验本身。

## 六、建议的受控实验矩阵

不要一次把数据、DPO、RL、视觉奖励全混进去。建议按以下顺序：

| 实验 | 新增内容 | 主要验证问题 |
|---|---|---|
| A | 当前混合 SFT | 现有基线 |
| B | 完整真实修复轨迹＋动作级选择性屏蔽 | 真实返修数据是否有效 |
| C | 学生真实状态上的教师纠偏 SFT | 学生中心数据是否优于单纯教师成功轨迹 |
| D | 同前缀的教师／学生分支偏好训练 | 能否改善关键决策和错误恢复 |
| E | 完整多轮 episode 的结果 RL | 能否进一步提高最终 Accepted@1 |
| F | 独立视觉过程奖励或视觉偏好 | 视觉信号是否有额外收益且未被钻空子 |

核心指标保持：

- **Accepted@1：唯一主指标**，在固定、充分的工具和时间预算下统计；
- 真实缺陷修复成功率；
- 视觉缺陷修复成功率；
- 非目标状态保持率；
- 健康场景误改率；
- 证据不足提前交付率；
- 旧截图误判率；
- 模型原因造成的循环和超时率。

首轮代码质量、首次可运行率、轮数、token 和耗时都可以报告，但都只作为诊断指标，不能压过最终成果质量。

## 七、你们现在最应该做的三件事

### 1. 先补齐“可恢复、可分支”的采集环境

没有快照恢复，就无法高效做学生状态纠偏、共享前缀偏好和短程 RL。这比先选择 GRPO 还是 DAPO 更优先。

### 2. 把“真实缺陷修复轨迹为零”变成学生失败覆盖表

围绕当前学生真实失败，分别采集：

- 执行错误修复；
- 机构和时间语义修复；
- 真实截图驱动的视觉修复；
- 局部编辑与非目标保持；
- 健康场景正确停止；
- 证据不足时继续检查，而不是提前交付。

第一批不必追求万级。先验证几十到几百个真实学生故障状态，能否稳定生产“恢复前快照→教师纠偏→学生继续→最终验收”的高质量数据。

### 3. 先证明学生中心数据的增量，再扩大 RL

如果教师纠偏 SFT 都不能明显提升真实修复能力，直接上长轨迹 RL 通常只会得到高方差、难归因的结果。若它有效，再把相同的学生前缀、失败分支和验证器用于偏好优化与多轮 RL，工程和数据都可以复用。

**修正后的最终路线就是：代码底座保留，完整 Agent 轨迹冷启动，学生中心纠偏作为主攻，分支偏好和短程 RL 解决关键决策，完整多轮 RL 最后放大最终验收能力。**这条路线与“质量优先、允许多次观察和返修”的目标是一致的，也比单纯堆教师成功轨迹或直接上单轮 RL 更符合你们的实际瓶颈。
