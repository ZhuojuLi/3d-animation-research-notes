可以先给一个直接结论：

> **学生可以优先试 35B‑A3B，但先证明它在你们的 3D Agent 任务上质量不降；教师常规用 `high`、难题救援和关键审核用 `max`；学生正式训练、失败采集、RL 和评测统一使用“思考开启＋保留历史思考”的高档。若学生服务支持 `low／medium／high`，我推荐 `high` 作为主档，`medium` 只用于工程联调，`max／xhigh` 作为质量上限对照。**

这里的核心不是“档位越高越好”，而是**让足够思考与充分环境反馈配合**。

## 一、35B‑A3B 值得试，但不要把它理解成“3B 模型”

如果你指的是 Qwen3.6‑35B‑A3B，它对你最有吸引力的地方确实是：

- 激活参数少， rollout 解码吞吐可能更高；
- 多轮 Agent 需要反复生成，推理加速能明显增加每天可完成的 episode 数；
- 更快的失败采集意味着 DAgger、RFT、分支偏好和多轮 RL 都能更快迭代；
- 省下来的时间可以用于更多真实返修，而不只是缩短单次响应。

但要注意三点。

### 1. 推理更快，不等于全参数训练也按 3B 规模变快

35B 总参数仍然要加载和保存。全参数训练时，梯度、优化器状态以及专家并行通信也不会只按 3B 计算。NVIDIA 针对同系列 MoE 视觉模型的微调 recipe 也明确使用专家并行配置，而不是普通 dense 模型的直接替换。

所以它最可能加速的是：

```text
学生 rollout
失败挖掘
配对评测
教师介入前的学生状态采集
多轮 RL 的环境交互
```

不一定加速的是：

```text
全参数 SFT 的单步训练
checkpoint 保存和加载
长序列 MoE 训练通信
```

### 2. 不要同时换基座、换数据配方、换思考档位

建议保留 27B 作为质量基线，按顺序做：

```text
第一步：27B 与 35B‑A3B 基座在相同 Harness 下配对比较
第二步：用相同数据做一轮短 SFT，再配对比较
第三步：确认 35B‑A3B 质量不降后，再切主开发线
第四步：最后单独比较学生思考档位
```

重点看：

- Accepted@1；
- 真实修复成功率；
- 视觉缺陷修复成功率；
- 工具格式错误率；
- 长上下文后的动作质量；
- 空回答、思考不闭合和输出截断；
- 每 GPU 小时完成的完整 episode 数；
- 每个最终 Accepted 成果对应的总墙钟时间。

**27B 不应现在就被判定“没必要”，它应该暂时保留为质量上限对照。**

## 二、教师思考档位：常规 `high`，关键任务 `max`

目前 Kimi K3 系列的官方接口支持 `low／high／max`，默认 `max`，并且始终开启思考与 Preserved Thinking。

结合你有充足 API token，我建议这样分工：

| 教师工作 | 推荐档位 | 原因 |
|---|---|---|
| 常规完整 Agent 轨迹采集 | `high` | 质量较高，轨迹通常更适合学生模仿 |
| 学生完全失败的难题救援 | `max` | 尽量提高最终成功率 |
| 首个关键错误归因 | `max` | 归因错误会直接污染纠偏数据 |
| 复杂视觉返修 | `max` | 需要综合多帧、多视角、状态和代码 |
| 最终独立审核 | `max` | 尽量降低错误验收 |
| 简单题目变体、格式转换 | `low` 或 `high` | 不必消耗过深推理 |

**如果教师侧只允许你选一个档位，我会选 `max`。**因为你的首要目标是数据质量，而不是节省教师 token。

但不建议所有数据都无差别使用 `max`，原因不是 API 成本，而是：

- 教师轨迹可能更长、更绕；
- 原始思考总量会增加；
- 长上下文采集和转换更困难；
- 学生可能学到不必要的长时间犹豫；
- 教师自行探索很久，并不天然等于更好的教学轨迹。

所以应以**最终独立验收通过率和轨迹可教学性**来决定，而不是以思考长度判断教师质量。

无限 token 消除的是 API 费用约束，并没有消除采集时间、上下文长度和学生模仿难度。

## 三、学生思考档位：正式主档推荐 `high`，不是盲目 `max`

### 我的推荐

如果学生服务支持多档推理：

```text
工程联调：medium
正式失败采集：high
SFT 后评测：high
DAgger／学生中心纠偏：high
多轮 RL rollout：high
最终默认部署：high
质量上限对照：max 或 xhigh
```

如果 35B‑A3B 的本地模板只提供思考开关，那么对应建议就是：

```text
enable_thinking = true
preserve_thinking = true
```

不要为了套用上面的名字，人为给模板添加它并不支持的 `high` 参数。

### 为什么学生主档不是直接 `max`

因为 Agent 的质量不是单纯由内部推理深度决定：

```text
最终质量
≈ 需求理解
× 代码能力
× 反馈利用
× 视觉观察
× 返修决策
× 正确停止
```

`max` 可能帮助复杂机构推理，却也可能带来：

- 简单工具操作前过度思考；
- 重复分析同一错误；
- 迟迟不执行有信息量的检查；
- 历史思考占用过多上下文；
- 长 episode 后半段决策质量下降；
- 思考变长但工具动作没有改善。

所以我建议把 `max／xhigh` 当成**必须实测的候选**，而不是先验答案。若它在你们的配对评测中确实提高 Accepted@1，而且不增加循环、空响应和提前停止，那就应该使用最高档——质量优先并不意味着回避这个结论。

## 四、严格来说，“训练档位”是数据与 rollout 协议，不只是训练参数

普通 SFT 前向计算时，并没有一个自动生成行为的 `reasoning_effort` 开关。真正决定学生学到什么的是：

- 数据中是否包含思考；
- 历史思考是否保留；
- 思考、动作和代码分别怎样计算损失；
- chat template 中的档位标记；
- 评测和 RL rollout 时使用什么推理配置。

因此需要遵守一条原则：

> **学生正式失败采集、RL rollout、模型评测和目标部署，应尽量使用同一档位、同一思考保留协议和同一上下文压缩策略。**

不要在 `medium` 下采集学生失败，却希望这些数据准确代表 `high` 部署时的错误分布；也不要把不同档位的 rollout 混在同一个 GRPO 优势组里，否则奖励差异可能只来自档位，而不是动作质量。

每条数据建议分别记录：

```text
teacher_model
teacher_reasoning_effort
student_model
student_reasoning_effort
preserve_thinking
max_completion_tokens
context_compaction_policy
tool_schema_version
```

### 教师的 `max` 思考不要原样高权重压给学生

教师用 `max` 不代表学生必须模仿教师的全部长思考。

建议：

- 动作、工具决策和代码监督权重高于原始思考；
- 对无意义重复、长时间犹豫和错误绕行降低或屏蔽损失；
- 重点保留“根据什么证据，为什么采取下一步动作”的推理；
- 比较“原始思考低权重”和“只监督关键思考／动作”的消融；
- 不因为教师思考更长，就提高它的训练权重。

此外，Kimi 教师采集时必须保留并原样回传完整 assistant message，包括 `reasoning_content` 和 `tool_calls`；官方文档明确要求不要只保留最终 `content`，否则多轮工具调用的推理上下文会断裂。 转换成学生格式时可以改变模板，但不能丢失思考、动作、工具结果之间的时间顺序和对应关系。

## 五、最小档位实验，不需要一开始就跑大训练

建议固定学生基座、数据、工具和预算，只改变思考配置：

| 组别 | 学生配置 | 目的 |
|---|---|---|
| S0 | 思考关闭或最低档 | 检查基础工具与代码能力 |
| S1 | `medium` | 快速开发基线 |
| S2 | `high` | 推荐主档 |
| S3 | `max／xhigh` | 质量上限 |

每组至少分别统计：

- 最终 Accepted@1；
- 首次可运行率；
- 执行错误修复率；
- 视觉错误修复率；
- 有效工具动作占比；
- 无意义循环率；
- 证据不足提前交付率；
- 上下文溢出和截断率；
- 完整 episode 墙钟时间。

选择规则采用**质量优先的字典序**：

1. 先选 Accepted@1 和盲审质量最好的档；
2. 如果质量差异不确定或基本相当，再选速度更快、轨迹更稳定的档；
3. 如果最高档只是思考更长，却没有质量收益，就不使用最高档。

**所以我当前的具体配方是：35B‑A3B 优先做学生候选；教师 `high` 批量造数、`max` 救援和审核；学生 `high`＋Preserved Thinking 作为训练、采集、RL、评测和部署的统一主档；`max／xhigh` 保留为配对实验中的质量上限。**这比“教师和学生都固定最高档”更稳健，也比为了开发速度统一降到 `medium` 更符合你质量优先的目标。
