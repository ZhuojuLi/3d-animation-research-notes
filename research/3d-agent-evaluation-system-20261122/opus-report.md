## 1. 总体判断

**结论：当前体系还不能支持首轮 SFT 选型。补完 §5 的 P0 后，它能支持的也只是粗粒度的放行/不放行判断，不能支持细粒度排名。**

1. **最大的问题是题目本身无效，比检查器偏松更严重。** 我逐个读了 8 个起始 fixture 的源码：真正成立的起始缺陷只有 3 个（摩天轮、暂停、点火）。另外 3 个的题面描述和 fixture 事实不符（火箭没有被裁切；机械臂"末端穿透"的位置描述错误；传送带题提到的料箱和接触在场景里根本不存在），1 个可能已经满足编辑目标（水车机位本来就在约 37°），还有 1 个缺少题面要求公开的状态字段（太阳能材质）。多方汇总把这批问题主要归因于"checker 弱"，但更根本的是 brief 和 fixture 不一致。仅靠校准检查器解决不了，需要独立的**题目有效性审计**。
2. **正在跑的 960 条采集用的仍是同类检查器。** `S/cases.json` 共 1,312 条断言，全部读取 Agent 自报的 `s.*` 状态。其中 64 个 case（含全部 48 个健康控制）的 128 条断言硬编码了 7 个固定采样时刻，命中不到的时刻一律 `return true`。按 best-of-3 选优只会放大这类假阳性。
3. **统计上，12×4 的 test 只能检出很大的差异。** 每题跑一次、每族 4 个二元 case 时，合理的配对题族差标准差约为 0.25–0.35，按 t 分布算出的 MDE 约为 22–30pp。真实提升 10pp 时检出概率约 18%（σΔ=0.3）。所以第一轮能回答的是"学生有没有大幅变好、有没有关键回归"，回答不了"one-shot 和多轮谁更好"。
4. **前提条件**（详见 §5）：
   - 先做题目有效性审计；
   - 代表题族要有不依赖自报值的测量，并配一个伪造状态的变异；
   - 健康控制和缺输入阻断移出主指标，单独作为配对的护栏指标；
   - 谱系改用分类型的边，dev/test 封存；
   - native 的 test 运行推迟到协议冻结后，和学生交错执行；
   - dev 上用 native 加现有 Aodi one-shot checkpoint 估计配对方差，再冻结 R 和判定规则。

多方研究的大方向是对的：分层门槛、评估器校准、按题族隔离、配对统计、unknown 不算成功。我没有为了显得独立而推翻这些。下面的意见集中在三类：证据显示汇总**说错**的地方、**说得不够**的地方，以及**和当前执行计划冲突**的地方。

## 2. 按严重性排序的问题清单

### 严重 1 [A]：题目有效性缺陷比检查器假阳性更普遍（8 个起始 fixture 逐个核验）

**证据**（题面均为 `P/evals/collection-v1/<case>.txt` 第 1 行，fixture 为 `P/evals/collection-v1/fixtures/<dir>/src/main.js`，预检结果为 `P/runs/collection-preflight/fixtures-v1/summary.json`）：

- 如果用这些题采集教师轨迹，会教学生去修不存在的缺陷（火箭）、按错误描述修改（机械臂）、捏造不存在的对象（料箱），或者把"补一个状态字段"当作完成编辑（太阳能）。
- 汇总 `R/README.md:116–119` 说"5/8 不是 5 个已证实的假阳性"，这一点正确，但还不够。按源码，5 个通过里**干净的假阳性只有 1 个（摩天轮）**，1 个是编辑目标缺失加 brief 错误（传送带），2 个是坏题（机械臂、火箭），1 个欠指定（水车）。
- 主报告 `R/main-report.md:35` 把太阳能题解释成"隐藏测试依赖题面没要求的名字、误杀合理实现"，这一点**不成立**：题面明确要求了 `panel_count`。

**修复**：在检查器校准之前加一个独立的 **T0 题目有效性检查**，每个带 fixture 的 case 都要过：
- (a) 题面里提到的对象和结构在 fixture 中存在；
- (b) 题面声称的缺陷能用可执行的测量复现（投影、重叠、角速度等）；
- (c) 起始 fixture 满足题面公开的观测 schema；
- (d) 编辑题的未编辑状态必须被拒绝。

程序化 fixture 的 (b) 可以直接用代码算，我在本审查里就是这样复算的。**P0。**

### 严重 2 [A]：正在运行的采集和全部题包都依赖自报状态；best-of-3 选优会放大假阳性

**证据**：
- `S/cases.json`（320 个 train case，`P/reports/scale-collection-20261122-001/collection-planned.json` 记 `planned_trials=960`，`collection-progress.jsonl` 已完成 21 条）中，1,312/1,312 条断言都读取 `s.*`。名为 `independent_witness` 的断言（例如 `lab-manometer-sweep`）读的也是 Agent 自己写的 `s.witness`，名字暗示独立，实际不独立。
- `check_claude_case.mjs:70–76` 先调用 Agent 提供的 `renderAt`，再读 `window.__getSceneState?.() || window.__3D_STATE__`；`:100` 用 `new Function` 在这个对象上求值。
- `run_claude_cases.py:154` 确认采集流程调用的就是这个检查器。
- `browser_probe` 字段（256 个 case）在 `S/generate.py:70` 只是拼进了**题面文字**，让 Agent 自己去做，检查器并不执行。
- 采集计划写明每题采 3 次并选优（`P/docs/plans/2026-11-22-overnight-react-collection.md:23–27`），选优依据包括"关键断言"。

**影响**：训练正例的准入依据，等于"Agent 写出的状态值满足表达式"。三次里只要有一次自报值通过就可能入选，所以 checker 的假阳性在 best-of-3 下的入选率高于单次。

**修复**：
- 采集可以继续：原始轨迹已归档，之后可以重新评分。
- 但**训练准入必须改用独立测量**。最小方案是把"公开观测契约"从"自报数值"改成"公开真实对象"：题面要求暴露渲染时用的 `scene` 和 `camera`，检查器直接从对象读取世界矩阵、投影和材质，再用自己的 renderer 重渲染这一对象，与页面 canvas 做像素比对，把对象和画面绑定。这是本审查提出的**设计建议**，项目里还没有实现。
- 每个代表题族配一个**伪造状态的变异**（自报值正确、场景是错的），检查器必须拒绝。

**P0**（指准入前，不是采集前）。

### 严重 3 [A]：检查器的几处结构性同义反复和静默放行

1. **首尾像素比较是同义反复。** `check_claude_case.mjs:66` 的采样包括 t=0 和 t=D；`:92–93` 比较两帧哈希。所有循环 fixture 的 `renderAt` 都先做 `t mod D`（ferris:9、arm:8、conveyor:9、watermill:8、solar:28），所以 renderAt(D) 就是 renderAt(0)，这项检查对任何取模实现恒为真，证明不了接缝处的位置或速度连续。
2. **只验证 seek 接口，不验证真实播放。** 除了暂停题，所有采样都走 `renderAt`（`:63,71`）。用户实际看到的 rAF 播放路径从未被检查。
3. **采样时刻固定、可预测且很稀疏**：`[0, 1/fps, .137D, .5D, .871D, D−1/fps, D]`。摩天轮 [5.8, 6) 的静止窗口里只有一个采样点，单点无法估计速度。
4. **`mode:"any"` 太弱**：7 个点里有一个非零就算"会动"（`cases.json:6,29,35,47,53`）。
5. **硬编码采样表、命中不到就放行**：`S/cases.json` 中 64 个 case 的 128 条断言用 `ts=[…7 个时刻…]; if(i<0) return true`。只要采样计划改动（比如改成随机或加密），这些断言会**静默全过**。这是项目里"未测被当作通过"的一个具体实例。
6. **unknown 被折叠成失败**：表达式抛错时记 `null`，再被判为失败（`:101–107`）；字段缺失时 `Math.abs(undefined)>x` 直接得 false。所以这个检查器里没有 unknown 状态；评测侧的"不可判"会全部记到模型头上。

**修复**：删除 `if(i<0) return true`；采样改为"均匀采样 + 关键窗口加密 + 每次运行从种子派生的随机审计时刻"；增加真实播放录制；断言输出三态 pass/fail/unknown。**P0**（第 5 项）、**P1**（其余）。

### 严重 4 [B，有 A 支撑]：健康控制被混进修复族的主指标，无操作策略可以白拿分

**证据**：
- `R/README.md:185` 和 `R/main-report.md:173` 建议修复族的 4 个变体中放"3 个单缺陷 + 1 个健康控制"，并一起计入 family 宏平均的 `Accepted@1`。
- `S/cases.json` 中 48 个健康控制的 `task_type` 全是 `repair`。
- `S/generate.py:145` 写明健康 fixture 来自"原交付通过技术检查"的旧成品，也就是只过了弱检查器，并未独立确认合格。
- 健康控制的断言是在 7 个固定时刻上比较自报状态是否等于基线（见严重 3 第 5 项），不是计划里说的"最终哈希未变"（`overnight:38`）。

**影响**：
- 一个"检查一下、原样交付"的无操作策略，在每个含健康控制的修复族里稳拿 1/4。一个"总要改点什么"的策略在健康题上失分，但可能修复更多真缺陷。两者被混成一个按 25% 患病率加权的准确率，而 25% 是随意定的。
- 如果旧成品本身带着未被发现的缺陷，健康控制会**奖励保留缺陷、惩罚修好它**。
- 主报告和 Astra 都要求"健康控制允许不修改"，这一点正确，但没有给出它在主指标里的适用性掩码。

**修复**：
- 主指标 `Accepted@1` 只统计应交付的生成、修复、编辑 case。
- 健康控制和缺输入阻断各自单独报告，并成对呈现：修复敏感性对健康特异性，正确阻断率对可完成题的误阻断率。
- 健康 fixture 必须先过 T0 和独立测量，不能用"旧检查通过"代替。

**P0**（主指标定义必须在 test 冻结前确定）。

### 严重 5 [A/B]：native test 基线的时点和封存，与"冻结后统一揭盲"冲突

**证据**：
- `overnight:86–93` 计划**今晚**新建 6 个 dev 和 12 个 test 题簇，并运行原版 Qwen 基线（"每题一次"）。
- 早晨交付物包括"所有 case、trial、状态、失败原因"（`:117–125`）。
- 难题定义要求"Qwen 失败可重放"（`:40`），训练批次 B 也优先从"Qwen 真实失败"派生（`:59`）。
- 汇总 `R/README.md:51` 允许"评测侧提前跑"，前提是训练和选型不据此调参。
- 我在 `P/evals/` 和 `agent-runs/` 中**没有找到 `split` 为 dev/test 的 cases.json**，说明 test 还没建好，现在纠正还来得及。

**影响**：
- (a) 今晚的 native 运行用的是今晚的 harness、提示词和观测 schema。P0 要改公开观测契约，题面会随之变化，所以这次运行**无法作为最终受控对照中的 native 臂**。
- (b) 同一批人同时设计训练难题，test 失败的分类信息会通过"Qwen 真实失败"回流到训练题设计；这不需要复制任何 test 题面。
- (c) 难度标签如果来自同一次 native 失败，用"因为失败才入选"的 case 去比较，存在**均值回归偏差**，会让任何学生显得更好。

**修复**：
- 我的独立选择比汇总更严：**协议冻结前不在 test 上跑任何系统**，基线改到 dev 上跑。
- 如果已经跑了，就由评测侧封存逐题结果，最终必须在冻结后**重跑 native**，和学生交错执行。
- 难度标签只能用 dev 或 pilot 上的运行，不能用最终比较的那次运行。

**P0。**

### 严重 6 [A]：family 标签不可信；汇总的"连通分量"规则无法照字面执行

**证据**：
- `collection-v1/cases.json` 中 12 个 case 有 12 个不同的 `family`，实际同源的约 6 组：
  - rocket-v1、rocket-framing-v1、rocket-edit-v1 共用一份源码，`diff` 只差 `camera.lookAt` 一行；
  - solar-v1、solar-pause-v1、solar-edit-v1 中，`solar-material` 和 `solar-pause` 只差 `if (playing)` 一处，也就是说**编辑题的起始工程恰好是暂停修复题的答案**；
  - 同理，`rocket` fixture（相机跟随）恰好是取景修复题的一个合理答案；
  - watermill 和 conveyor 各有两个标签。
- `S/cases.json` 已有 `lineage_ids`，这是进步。但我对全部 lineage 标签做并查集，**320 个 case 只得到 1 个连通分量**，因为 `protocol:sweep`、`mechanism:*`、`template:*` 这类分类标签连通了所有题；排除这些分类标签后是 68 个分量，而标注的 family 是 54 个。

**影响**：按"同 lineage 即同族"的字面规则，要么全集不可切分，要么有人凭直觉删边，切分就变得不可复查。同一份工程的修复题和编辑题跨 split 时，就是**直接的答案泄漏**。

**修复**：谱系边分成两类：
- **泄漏边**：源码、fixture、资产、参考解、教师轨迹、缺陷注入器；只对这类边求连通分量。
- **分类标签**：机制、协议、模板风格；用来定义 OOD 轴，不用来合并。

另外，"某题的 fixture 是另一题的答案"要作为显式检查项。**P0**（dev/test 建立之前）。

### 严重 7 [A，统计复算]：几处统计口径有误或承诺过度

所有数字都用 scipy 复算过。

1. **family 宏平均和 case 微平均的争论，在均衡设计下没有意义。** 12×4、每题 R 相同时，两者**数值完全相等**。只有在适用性掩码剔除 case、infra 或 unknown 改变 `R_fc`、或者各族 case 数不等时，两者才会分开。真正要定的是**区间按 family 聚类**，以及在这几种情况下的权重规则。
2. **48 case 上的 McNemar 应删除，不应作为推断方法。** `R/README.md:192,199` 保留了"单次二分类可补精确 McNemar"。这忽略了每族 4 题的簇内相关，p 值会偏小，第二份外部报告（`external-report-2.md:433`）对此的判断是对的。15:5 → p=0.0414、8:2 → p=0.1094 这两个算术本身没错，但主报告 `:193` 说 8:2"点差更大"是**错的**：12.5pp 小于 20.8pp，只是不一致对的比例更悬殊。
3. **MDE：精度花错了地方。** 校对笔记 `R/external-report-2-review.md:41–48` 把正态分位数精确到 10 位小数，但这里的主要误差来自用正态代替 t，以及 σΔ 本身未知：

| F | σΔ | 正态 MDE | t(F−1) MDE | Holm 第一检验（α=.025，t） |
|---|---|---:|---:|---:|
| 6 | 0.10 | 11.4pp | **14.3pp** | 16.7pp |
| 12 | 0.10 | 8.1pp | 8.9pp | 10.0pp |
| 12 | 0.30 | 24.3pp | **26.6pp** | 30.0pp |

   σΔ=0.10 在 R=1、每族 4 个二元 case 时并不现实。两系统都约 50% 成功、案内相关 ρ=0–0.5 时，σΔ≈0.25–0.35。对应的 t-MDE 约为 22–31pp。真实提升 10pp、σΔ=0.3 时检出概率约 18%；提升 20pp 时约 56%。
4. **12 簇的 percentile bootstrap 偏窄。** 它的标准误是 s·√((F−1)/F)/√F，再配合 1.96，宽度只有 t(11) 区间的约 **85%**。汇总 `R/README.md:197` 把它定为主区间，我建议主区间改用**题族配对差的 t 区间，或符号翻转区间**；bootstrap 和逐一删族作为敏感性分析。二元小族的 d_f 只能取 0.25 的整数倍，常会出现 d_f=0，符号翻转的有效族数会进一步减少。
5. **只有 native 的 pilot 能估计什么。** 第二份校对笔记（`:52`）说它不能估计跨系统配对方差，这是对的。但它**可以在 ρ≥0 的假设下给出 σΔ 的上界**：σΔ² ≤ σA² + σB²。更好的做法是项目里已有 Aodi one-shot checkpoint（scale 计划 `:29`），可以直接和 native 在 dev 上配对实测 σΔ。
6. **头条区间会误导。** `R/README.md:24` 的头条"48 中 24 通过，Wilson 36.4–63.6%"是把 48 题当独立样本算的。按 12 个簇等效计算，区间约为 25.4–74.6%。头条应给聚类后的口径。

**P1**（必须在 test 冻结前写进分析脚本）。

### 严重 8 [A]：外层 harness 的分母语义和提议的协议不一致，"replay"一词存在命名冲突

- `skills/agent-harness/templates/iterate/metrics.py:145–149`：一个 case 只要有任一 trial 的 `pass` 为 None，整题就从分子**和分母**里剔除（`:167–173` 再按剩余 case 求均值）。这是完整病例分析：如果 unknown 集中出现在失败题上（比如页面卡死导致评分器崩溃），均值会被抬高。这是"unknown 伪装成通过"在代码里的真实路径。
- `metrics.py:52–53`：usage 缺失时记为 0，会低估成本（Astra 也指出过）。
- `replay.py:97–102`：评分器超时记为 `check_ok=False`，即模型失败；进程异常也没有 infra 分类。
- **命名冲突**：`replay.py:2,17` 中的"replay"是**重新运行 Agent，会产生真实模型调用**。汇总和外部报告说的"evaluator replay 不给模型额外动作"（`R/README.md:69`，校对笔记 §5）指的是对冻结产物重新评分。同一个词两种意思，有人按字面"replay 一次"就等于给某个模型多了一次尝试。建议把只重评分的操作命名为 `rescore`，并强制通过 `planned_trial_id` 关联。

**P1。**

### 严重 9 [B]：校准设计依赖作者自己写的变异，缺少真实输出的校准

- 好版、单缺陷版、替代版、健康控制四件套由写检查器的同一方编写，盲点会重叠：作者想不到的缺陷，作者写的变异也覆盖不到。本次发现的"臂杆底端嵌在包裹里"恰恰不是任何人设计的变异。
- 第二份外部报告提出把校准集拆成设计集和冻结验收集（`R/README.md:100`），方向正确。但首轮只有 4 个代表题族，按族拆只剩 2+2，几乎没有统计意义。
- **建议的 holdout**：(a) 由不读检查器代码的人或另一个 AI 盲写变异；(b) 从真实 Qwen 和 Kimi 输出中分层抽样，人工判定后计算检查器在**真实输出**上的混淆矩阵。

**P1**（4 族起步时 (a) 和 (b) 至少做一项）。

### 严重 10 [B]：视觉评审的若干解释和设计缺口

- **VibePrevisBench 0.73–0.76**：根据第二份外部报告的转述（`external-report-2.md:117`），这是**两个 VLM 判官之间**在单 run 层（2,628 runs）的 Spearman；agent 层为 0.96；人类偏好只在 agent 层比较（约 0.90–0.92）。如果转述准确，它衡量的是判官间**一致性**，不是**正确性**：两个判官可能共享偏差，并且该数据跨 242 个任务合并计算，任务间难度差会抬高相关。它也说明不了二元 `V_min` 阈值处的一致率。汇总"均值相关高不代表单视频可靠"的方向是对的，但应收紧为"**单 run 的判官对人类的效度没有报告**，本项目必须自测"。**我没能在线核实原文**（WebFetch 被拒绝），这一条标为待核实。
- **prevalence**：校准集里人为富集了缺陷，其中的 κ 和一致率受患病率影响。应分别报告阳性一致率和阴性一致率，误报率要按真实运行中的患病率重新估计。汇总 `R/README.md:75` 已经提到，这里保留。
- **dev 和 test 用的指标不同**：dev 用不含 `V_min` 的 `Functional@1` 选模型，test 用含 `V_min` 的 `Accepted@1` 验证。dev 只有 12 题，`V_min` 人工成本很低，应该在 dev 上也评，否则选型目标和验收目标不一致。
- 取景、裁切这类可测项（例如火箭投影边距）应优先用**实测**判定；人工的 `V_min` 只留给"动作能否看懂"这类语义可读性问题。

**P1。**

### 严重 11 [C]：资源与并发会影响墙钟预算的公平性

- Kimi 采集用 16–32 路并发，Qwen 单并发（`overnight:44`、`scale:17`）。SwiftShader 渲染完全占用 CPU。单题墙钟上限是 3600 s。native 和学生如果在不同的 GPU 或 serving 栈上运行，解码速度不同，同一个墙钟上限对两边意味着不同的预算。
- **修复**：预算以步数和 token 为主，墙钟只作为宽松的安全上限；记录超时、实际并发和机器负载；各臂按 case 交错运行。我不建议首轮就做 1x–3x 的资源余量校准，那属于过度工程。**P2。**

### 严重 12 [A]：`check_case.py` 把作者自审设为通过条件，会筛选出"总说通过"的轨迹

- `P/scripts/check_case.py:56–57` 要求 `review.verdict=='pass'`。诚实报告视觉缺陷的模型会被判失败，过度声称的模型可以通过。用它筛教师轨迹，会系统性偏向"自称通过"的行为。
- `:53–55` 信任工作区中的 `browser-report.json`，不重新运行浏览器。这一点有 `animation_agent/runtime.py:48` 的写保护缓解（模型不能写 `output/` 和 `work/candidates/`），风险较低。
- **修复**：自审结论只作为诊断字段，不作为门槛。**P2**（Claude Code 采集流程不走这个脚本）。

### 严重 13 [A，低]：报告中的小的引用或表述错误

- `R/main-report.md:33` 写的是 `window.__getSceneState__?.()`，源码 `check_claude_case.mjs:73` 是 `window.__getSceneState?.()`，名字不同。
- `R/main-report.md:35` 对太阳能题的解释有误（见严重 1）。

### 4.1 共识中需要收紧或纠正的

1. **"先校准检查器，再采集"** → 收紧为 **"先校准题目，再校准检查器，再准入"**。题目无效（严重 1）是更普遍的问题，四件套发现不了它：如果"坏版"本来就不坏（火箭），校准表只会显示"检查器漏检"，掩盖真正的原因。
2. **"5/8 不是 5 个已证实假阳性"** → 正确，可以细化为"1 个干净假阳性、1 个编辑目标缺失加 brief 错误、2 个坏题、1 个欠指定"（严重 1）。
3. **"同源即连通分量"** → 必须给出边的类型，否则无法执行（严重 6）。
4. **"健康控制 = 不误改"** → 定义正确，但：(a) 不能并入主指标；(b) 健康 fixture 必须独立确认合格；(c) 第二份外部报告 §4.1 说的"健康控制"其实是**评估器层面**的无误报控制，校对笔记把它一并当作误解来纠正，有点过度。那个概念应并入"好版/替代版"控制，不要因为名字相同而丢掉。
5. **"unknown 永远不算成功"** → 正确，但不够。现实里更常见的是**根本没测**（材质、接缝速度、料箱），它既不是 unknown 也不是 fail，而是直接通过。需求覆盖矩阵（§3.1）是必要的补充。
6. **"允许评测侧提前跑 test"** → 我不采纳，理由见严重 5。
7. **MDE 精确分位数** → 方向有价值，但精度花错了地方（严重 7）。
8. **"只有 native 不能估计配对方差"** → 正确，但可以给上界；而且项目里已有现成的第二个系统（Aodi one-shot）。

## 5. 最小 P0 放行清单与可延后事项

### 5.1 P0：扩大采集规模或训练准入之前必须完成（按执行顺序）

正在跑的 960 条采集可以继续：原始数据已归档，可以重新评分。但**不要把规模扩到 960 条以上，也不要让任何轨迹进入 SFT**，直到以下 1–5 在 4 个代表题族上跑通，并应用到准入的 case 上。

1. **冻结现状的语义**：给现有全部 `check_ok` 加注"仅为候选标记，不是准入证据"；best-of-3 的最终选优推迟到新检查器就绪之后。
2. **T0 题目有效性审计**：对每个带 fixture 的 case 做严重 1 中的 (a)–(d) 四项。立即修复或作废 rocket-framing、arm-contact、edit-conveyor-arm、edit-watermill-camera（写明方位角容差和方向）、edit-solar-material（起始 fixture 补齐公开字段，或让题面不再要求）。健康 fixture 同样要过这一关。
3. **4 个代表题族的独立测量**：摩天轮接缝、机械臂接触、火箭取景、局部编辑各一个。从真实对象或重渲染的像素中取证据；每族配好版、单缺陷版、合理替代版、**伪造状态变异**，编辑题再加**未编辑状态**（必须被拒）。检查器必须全部判对。
4. **去掉静默放行**：删除 `if(i<0) return true`；采样加入接缝和事件窗口的加密点和随机审计时刻；断言输出三态。
