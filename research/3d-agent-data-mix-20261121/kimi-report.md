# 3D Agent 通用代码数据与难点任务簇配比：独立调研

> 公开整理版 · 2026-11-25。保留成文时点的记录；计划、文献结果和本地实测请分别理解。 环境路径已泛化，未收录的附件已标注；发布范围见 [整理说明](../../PROVENANCE.md)。

2026-11-21—2026-11-22。本文是主调研方的独立报告，未使用 Astra 的结论。研究对象是 **Qwen3.8-27B 的 Three.js 多轮 Agent SFT**，不是继续预训练，也不是在线 RL。

## 一、结论速览

1. **没有找到 OpenAI 或 Anthropic 公开的“通用代码数据 : 高难度 Agent 任务”生产模型标准配比。** OpenAI 明确公开了真实工作流训练和 RL 方法，但新一代技术报告通常不披露数据构建细节。Anthropic 的 A3 和审计训练披露了特定研究配置，但不能当作 Claude 的通用训练配方。
2. 最直接的公开参照是 **AgentTuning**：1,866 条经验证的 Agent 轨迹与通用指令混合，作者在 7B 上把 Agent 分布权重从 0 到 1 扫描，最终选择 **20%**。纯 Agent 数据的留出任务泛化反而更差。这个 20% 是训练目标中的数据分布权重，不是原始 case 数占比。
3. 其他公开数字差异很大：继续预训练的 Hephaestus 约 **36% Agent**；DeepSeek-R1 第二阶段 SFT 为 **75% 推理 / 25% 非推理样本**；Anthropic A3 的固定随机基线为 **85% 定向生成 / 15% 通用后训练**。它们训练阶段、目标和分母都不同，不能互相套用。
4. **对本项目，建议把 80:20 当作 500 个独立 Agent case 后的中心实验点，而不是当前 150 case 必须硬凑的比例。** 当前只有约 150 条合格轨迹时，若每 case 对应一条训练序列，先从 **95:5 的通用代码 : Agent 源采样权重**做保守端到端 run 更合理；随后在同一批数据上比较 100:0、95:5、80:20、65:35。
5. Agent 增量内部建议以 **50–60% 难点簇、25–30% 中等近邻变体、15–20% 基础与健康控制**为采集起点。难点是最大的一类，但不应是全量。健康控制教模型“检查后可以不改、可以交付”，避免只学会不断找错和过度编辑。
6. 真正需要同时管理三本账：**独立任务簇数、训练采样/目标权重、实际计入 loss 的 token 数**。只报其中一个，无法判断 Agent 能力是被淹没还是被过拟合。

一句话直觉：**开源代码数据负责“会写、写得广”，难点任务簇负责“会查、会修、会交付”；前者保持大头，后者用较少但高杠杆的有效训练权重改变行为。**

## 四、前沿理论真正支持的四条原则

### 1. 先修任务和标签，再谈配比

AgentTuning 的过滤消融显示，未过滤轨迹训练效果明显更差。A3 同时生成触发失败的题与外观相似的正常题。难点任务必须有：可运行初始状态、已知好版/坏版、独立断言、经审核的教师成功轨迹。教师也失败的“前沿难题”只能进入诊断池，不能冒充 SFT 正样本。

### 2. 按失败机制组织任务簇，而不是随机堆难题

一个难点簇应包含同一能力的不同状态和因果分支。例如“画面两球接触”至少包含真实三维穿插、仅投影遮挡、原本合格三种状态。这样才能学习“取得什么证据 → 选择什么动作”，而不是背某个源码补丁。

### 3. 通用数据不仅防遗忘，也提供 Agent 泛化所需能力

AgentTuning 的纯 Agent 组在未见任务上更差；Hephaestus 也保留文本与代码。对本项目，通用 CCORE/代码数据仍负责场景表达、几何与程序结构，难点轨迹负责时钟、接触、镜头、局部编辑、复验和交付。两者不是互相替代。

### 4. 最优比例是模型、阶段、数据量和评价目标的函数

AgentTuning 在 7B 上扫描后选 20%，Hephaestus 在继续预训练中得到 36%，A3 则根据失败类型自适应调权。论文支持的是**小规模、固定预算、留出任务上的配比扫描**，不是跨领域通用常数。

## 五、为什么 case 比例和训练比例不是一回事

### 5.1 三本账

1. **独立任务簇数**：衡量覆盖与多样性；同源的故障、镜头和参数变体不能算独立题族。
2. **训练序列与采样权重**：决定各来源被抽到的频率；一整条轨迹与按前缀展开的决策序列不是同一分母。
3. **实际 loss token**：只统计 assistant 正文、代码和工具调用中真正计 loss 的标签，不把 system、长工具结果和图片上下文当作监督量。

设 Agent 源采样概率为 \(p\)，每次抽到 Agent 与通用样本后的平均监督长度分别为 \(\bar\ell_a,\bar\ell_b\)，则实际 Agent loss-token 份额为：

\[
q=\frac{p\bar\ell_a}{p\bar\ell_a+(1-p)\bar\ell_b}.
\]

长轨迹的输入 token 会显著增加训练成本，但若这些 token 被 mask，它们不等于 \(q\)。报告训练配方时至少同时列出 \(p\)、\(q\)、独立簇数和优化步数。

### 5.2 当前数据的直观换算

现有 10,697 条通用代码记录。若首批得到 150 条合格 Agent 轨迹：

- 原始记录条数占比只有 \(150/(10697+150)=\mathbf{1.38\%}\)。
- 到 500 条时也只有 \(500/(10697+500)=\mathbf{4.47\%}\)。

若每个 case 只对应一条训练序列，以通用数据完整过一遍为一个基准，为达到 Agent 采样概率 \(p\)，每条 Agent 序列平均出现次数为：

\[
r=\frac{p}{1-p}\times\frac{10697}{N_a}.
\]

| Agent 源采样权重 | 150 条时平均重复 | 500 条时平均重复 |
|---|---:|---:|
| 5% | 3.75 次 | 1.13 次 |
| 10% | 7.92 次 | 2.38 次 |
| 20% | 17.83 次 | 5.35 次 |
| 35% | 38.40 次 | 11.52 次 |

这说明：**150 条时强行做 80:20，很可能是在做高频重复，而不是增加能力覆盖。** 若一条轨迹展开成多个有监督决策序列，应使用实际序列数重算，但这些序列仍不是独立 case；既要重新计算重复率，也要保留任务簇上限。

## 六、对本项目的量化建议

### 6.1 通用底座与 Agent 增量

以下全部是**本报告的实验建议，不是公开论文已证明的 Three.js 最优比例**。比例指来源的采样/优化权重，实际 loss-token 份额另行记录。

| 阶段 | 建议 | 目的 |
|---|---|---|
| 当前约 150 条合格轨迹、首轮打通 | **95:5**；若按决策展开，则按展开后的真实序列和重复率重新计算 | 降低小池高频重复和教师风格过拟合，先确认 Agent 增量有正收益 |
| 扩到约 500 个 case、覆盖多个难点簇 | 以 **80:20** 为中心配置 | 与最直接的 AgentTuning 公开扫描锚点对齐 |
| 配比压力测试 | **65:35** | 观察更高专门数据权重能否继续提升，以及何时损伤通用代码与健康控制 |
| 必要对照 | **100:0** 和 **90:10** | 分别确认 Agent 数据本身有增益，并补齐 5% 到 20% 之间的曲线 |

如果只允许先跑一次，当前采用 95:5；如果已经拥有约 500 个覆盖充分且验收通过的独立 case，则优先 80:20。不要为了套用 80:20 而把 150 条轨迹平均重复近 18 次。

### 6.2 Agent 增量内部的难度结构

建议首批按 **50% 难点、30% 中等、10% 基础、10% 健康控制**采集。难点占到 50–60%、中等占 25–30%、基础与健康控制合计占 15–20% 都可作为相邻配置。

以 200 个 case 为例：100 个难点、60 个中等、20 个基础、20 个健康控制。

- **难点**：原版 27B 在同一能力上稳定失败，但教师能在同一沙盒里完成，独立验收能确认；不是单纯更长、更花哨。
- **中等**：模型有时能完成，需要根据执行/视觉反馈返修，提供难点与基础之间的学习台阶。
- **基础**：短而正确的生成、编辑和交付，防止模型为了“显得会工作”而增加无效步骤。
- **健康控制**：初始产物已满足要求，正确动作是检查后保持并交付，或无证据时明确无法验证，而不是误改。

这里的 50:30:10:10 同样是待验证起点。Anthropic 审计的 50% 无异常校准只支持“健康控制不可缺”，不支持照搬它的具体比例。

### 6.3 配比之前先做两级均衡

1. **先按难点机制/任务簇均衡**，再抽簇内变体，避免某个容易批量生成的接缝或相机模板占满 Agent 份额。
2. **再按难度与任务类型检查覆盖**，生成、修复、局部编辑都要出现，但不必机械地各占三分之一；按真实失败分布调整。

论文和理论主要用来发现难点、设计对照与验收，不建议把“前沿理论文本”当成第三大块训练语料按篇数配比。除非目标改为理论知识和方法选型的文本灌注，那应另开数据域与评测。

## 七、最小可解释的实验矩阵

在同一原版 27B、同一批合格 Agent 数据、同一优化步数或训练 token 预算下比较：

| 组 | 通用代码 : Agent | 回答的问题 |
|---|---|---|
| A | 100:0 | 通用代码底座本身能做到什么 |
| B | 95:5 | 少量高杠杆 Agent 数据是否已有增益 |
| C | 80:20 | 公开 Agent SFT 锚点是否迁移到本任务 |
| D | 65:35 | 更高专门权重何时开始重复、遗忘或过度操作 |

训练时必须记录：独立题簇数、导出序列数、来源采样概率、每源监督 token、总输入 token、每 case 实际曝光次数、优化步数、截断/删除数。不能只记录磁盘上的数据条数。

在独立题簇上至少看四组指标：

1. 难点正式交付率与全部必要断言通过率。
2. 修复/编辑的目标成功率、非目标保持率和健康控制误改率。
3. 基础代码生成与简单 Agent 题回归。
4. 每次成功的时间、token、无效工具调用和超时率。

6 个 dev 题簇只适合粗略排除坏配置，不足以精确证明 15% 与 20% 的优劣。最终 test 应按场景、资产和模板家族保持隐藏，不能根据 test 反复调比例。

若后续要单独验证“难点是否是核心”，在选定通用/Agent 总比例后，再比较 **难点为主** 与 **随机/一般 Agent 轨迹为主**，保持教师、总监督 token 和训练预算一致。否则总配比和难度效应会混在一起。

## 八、最终判断

用户提出的方向与公开证据一致：**规模化开源数据是底座，真正拉开差距的是从真实前沿失败提炼的可验证能力任务簇。** 但“核心”不等于必须占训练数据的大多数。少量高质量、多轮、带真实反馈的轨迹可以承担行为塑形；大量通用代码负责保持覆盖与泛化。

因此，当前最值得执行的不是寻找一个普世 8:2 或 7:3，而是：

1. 先积累可运行、可独立验收、按难点机制分簇的 Agent 数据。
2. 小池时从 95:5 保守起步，扩池后以 80:20 为中心。
3. 用相同数据与预算做配比扫描，同时报告独立簇、采样权重和 loss token。
4. 用真实运行、返修、非目标保持和健康控制决定最终比例。
