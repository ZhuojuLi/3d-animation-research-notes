## 一、执行摘要

1. **首版训练里，ReAct 的"10.98% / 12.14%"是 token 曝光口径，优化器看到的更接近 2.3%。** 训练是 `global_batch_size=1`、`calculate_per_token_loss=True`、`clip_grad=1.0`，已记录的 440 条日志里梯度范数全部大于 1（即每一步都被裁剪到同一范数）。在这种设置下每一行样本贡献一次量级相同的更新，ReAct 是 10,946 步里的 249 步（2.27%），峰值学习率 1e-6，每条只见一次。**首版学生实质上是"一万条 CDN/r160 单轮代码 SFT + 极小剂量 ReAct"**，不应期待明显的 Agent 行为变化。
2. **"10.98% 落在 90:10 目标区"是因为中途把 thinking 纳入监督。** 11-21 计划写的是"首版不监督 thinking"；实际 thinking 权重 0.5，占 ReAct 监督位置的 57.3%。按原计划口径（只算正文和工具调用）ReAct 只占 5.00%。这个变化没有在计划或决策文档里找到依据。
3. **最终 249 条的任务构成与原设计偏离很大。** 11-21 计划是生成 60 / 修复 80 / 编辑 60；最终是生成 221（88.8%）、"修复" 23、局部编辑 5。而这 23 条"修复"**全部是健康控制（检查后不改）**，带真实缺陷的修复题计划只有 4 个，最终入选 0 条。由预实验真实失败派生的题族（挖掘机、发动机、工厂分拣、轨道对接、波干涉、太阳能等）在最终集中全部消失，剩下的主体是 32 个"实验台测量"模板题族。
4. **"难点 40%"只是题面复杂度标签。** 320 个规模化题的 `difficulty_evidence` 全部是 `prompt_complexity_only`；Kimi 在 hard 题上的单次技术通过率（85.4%）与 medium（86.8%）没有差别；Qwen 没有在这 320 题上跑过任何一题。
5. **质量门禁是采集之后才加的，代价很大。** 定帧漂移与 640 可读性两项在采集后才成为排除条件，共排除 384 条技术候选（规模化 345 + Aodi 39）。其中至少 73 条漂移排除来自**"健康" fixture 自身就漂移**（另有 5 条修复题很可能同源），对应约 90 条 trial 在开跑前就注定不可能入选。Aodi 队列 576 条 trial 中 480 条（83.3%）因题面没有说明 `file://` 单文件要求而失败——这是题面/检查器契约缺陷，不是模型能力。
6. **同题 3 次选优把"每题有主样本"的比例从约 27–50% 抬到 66%**，并且 76% 的主样本（161/211）按"耗时最短"选出。最终集描述的是 Kimi 的 best-of-3 加人工筛选，不是 Kimi 的单次能力。
7. **训练/推理不一致有几处是具体可查的**，不只是"缺 system"：并行工具结果在训练里被拆成独立 user 轮（2,604 处，官方模板是合并在同一轮）；65.6% 的工具调用里带有含题目 ID 与 trial 号的绝对路径；42.6% 的轨迹含写 Claude Code 自动记忆文件的调用（由未捕获的 system prompt 引起，却以权重 2.0 被监督）；底座 100% 用 CDN 而 ReAct 要求离线。
8. **评估目前无法支持任何"训练带来提升"的结论**：Qwen 基线只有 4 题且与训练 fixture 同血缘；新冻结的 60 题 holdout（我在给定证据之外发现，见 F 节）还没有跑任何基线，而且题型协议与训练数据差异很大；没有 100:0 的纯底座对照。

下一版最高杠杆的四件事（详见第四部分）：把最终门禁前移成题面契约和工作区内可执行的自检；补请求级捕获并用推理同一模板渲染训练数据；先把评估与基线跑起来再造数；用"更新步数"而不是 token 来设定并报告 ReAct 剂量。

## 三、主要坑

### B. Kimi 构造方式

**配置**【实测】：`kimi-k3`、`--effort medium`、通用 Claude Code 2.1.170、工具 `Read,Write,Edit,Bash,Glob,Grep`、单 trial 3600 秒、同题 3 次、16 路后切 32 路（`scripts/run_claude_cases.py:21-26,123-127`，`collection-planned.json`）。

**站得住的部分：**

- 通用 Claude Code、无专用 harness，使教师轨迹与学生将来的运行环境同构，这是正确方向。
- 3600 秒对 Kimi 足够：规模化 trial 耗时中位数 1,387 秒、P90 2,071 秒，只有 5 条超时。
- 切到 32 路前后，按小时分桶的技术通过率没有可见下降（切换发生在 11-22 07:34 UTC，前后都在 0.74–1.00 间波动）。切换本身中断并重跑了 16 条进行中的 trial。
- 原始流、失败、备选全部保留，可追溯性好。

**问题：**

1. **best-of-3 抬高了表观质量。**【实测】每题"耗时最短的技术候选"通过后续质量门禁的比例是 157/319=49.2%。第 1 次 trial 的 276 条技术候选中，117 条被排除、87 条成为主候选、72 条未被选中也未见复核——所以含质量门禁的"Kimi 单次通过率"在 **27.2%–49.7%** 之间（87/320 到 159/320），而 3 次选优后有主候选的题是 65.9%。Aodi 侧单次技术通过 18.2%，3 次内 37.0%。**最终数据集是教师 best-of-3 的产物；学生学到的轨迹里没有"这类题教师有一半以上概率交不出合格品"这个信息。** 这也与 11-21 计划的"不靠同题重复采样""质量失败的教师轨迹不反复采样择优"相反，属于中途改变的决定（11-22 计划已明示）。
2. **选优规则偏向短轨迹。**【实测】211 条主候选里 161 条的 `selection_reason` 是 `lowest_wall_seconds`；主候选是同题最快的占 138/211；主候选耗时是同题其他技术候选均值的 0.84 倍（中位数），轮数 0.89 倍。偏差幅度不大，但方向是"少验证、少返修"，与想蒸馏的"观察→修改→复验"相反。
3. **公开检查器只检查页面自报状态。** 207 条规模化记录的首条用户消息都含"公开采样表达式"，例如 `Math.abs(s.manometer_reading-(u=>2+u)(s.u))<=0.015`。题面写了"禁止将理论 f(u) 直接填为观测"，但检查器无法区分"从几何量出"和"直接填公式"。我抽看了 3 个主候选的源码，注释与结构显示是从几何/射线量取（如 `lab-manometer-sweep/trial-3/.../main.js:531`），**但这只是抽样，不是验收**。另外教师普遍把公开表达式抄进自己的 `verify.mjs` 当作自检——学生学到的是"题面给了判分表达式就照着写自检"，而新 holdout 的题面没有这种表达式（见 F）。
4. **Aodi 题面自相矛盾且漏了关键约束。** 例如 `evals/aodi-react-v1/prompts/aodi-scenes-v1-001.txt` 前一句是"只用本地安装的 Three.js，不要用 CDN"，后一句保留了原文"using Three.js from cdnjs"。`OUTPUT_CONTRACT`（`run_claude_cases.py:22-26`）只说"offline, self-contained"，没有说"必须能从 `file://` 直接打开"。教师交付了 import map + ES 模块（在它自己起的本地 HTTP 服务上验证通过），检查器用 `file://` 打开即 CORS 失败。按 11-22 计划自己的规则，这应记为 `invalid_case`（系统性 fixture/checker 缺陷），而不是模型交付失败。**存活的 88 条是"恰好做了内联打包"的子集，这是按交付形式筛选，不是按质量筛选。**
5. **环境泄漏给教师的信息。** 工作目录是 `…/kimi/<case-id>/trial-N/workspace`。case ID 直接写明题型和答案方向（`audit-*` = 健康控制，`fix-terminal-inventory-*` = 缺陷名）；同题其他 trial 就在 `../trial-1`。21 条跨 trial 读取/复制就是由此产生的。此外所有 trial 共用一个 `CLAUDE_CONFIG_DIR`，教师会话加载了用户个人的 skills 列表（`system.init` 事件里可见 `weekly-meeting`、`public-showcase` 等），并开启了自动记忆。
6. **无专用 harness 的代价是"环境噪声被当成行为"。**【实测】最终 249 条里有 10 条轨迹出现无头 Chromium 的 WebGL context lost 相关内容；240 条提到 SwiftShader。这些是采集机环境特征，会原样进入监督。

### C. 质量门禁各自说明了什么

| 门禁 | 实测 | 说明的问题 |
|---|---|---|
| 定帧漂移（`render_at_wallclock_contract_failure`） | 规模化 209 + Aodi 39 = 248 条，占被复核候选的 37.6%（248/659） | 契约只写了"用绝对时间、不用墙钟"，没有写"`renderAt` 之后画面与状态必须保持不变"；采集时的检查器只做相邻两次截图比较。**门禁定义晚于采集。** |
| 其中 fixture 自带漂移 | 健康控制 57 条、局部编辑 16 条，共 73 条；另有 fix 题 5 条漂移排除很可能同源（推断） | 健康控制的 57 条漂移排除全部落在 11 个 fixture 上（solar-material、engine-cutaway、forklift、fourbar、rocket-mission、scissor-lift、solar-offline、solar-pause、differential、excavator、geneva）。在这些 fixture 上，技术通过的审计 trial 除 2 条先因跨 trial 被排除外，**其余全部被漂移排除**。教师正确地"保持原样"，却因 fixture 本身不合格被排除。`fixture-preflight.json` 用的是旧检查器。涉及 30 个 case、90 条 trial。 |
| 640 可读性 | 136 条，集中在 target 协议（45）和各 hard 协议 | 题面没有给目标视口；带 HTML 控件面板的题在 640 宽下遮挡机构。教师一般只在 1280 下自检。 |
| 跨 trial 读取 | 21 条（结果读取 15、复制 5、审计产物 1） | 目录隔离不是访问隔离。扫描器自述"不保证穷尽"。 |
| 续跑上下文不完整 | 2 条（转换阶段才发现） | 一个 stream 里追加了多个会话，最后一段引用了未捕获的历史。应在采集器层面禁止同目录续跑，而不是在转换时排除。 |
| 工具错误反馈 | 最终集 12,450 次工具结果里 396 次 `is_error`，分布在 179/249 条轨迹 | 错误反馈本身是有价值的上下文；但**引发错误的那次工具调用也以权重 2.0 被监督**，等于让学生模仿出错的调用。 |
| 连续视频与完整语义 | 未做 | 现有"通过"= 公开状态断言 + 抽帧初审。运动是否连续、读数是否真从几何量出、修复/编辑是否真的达成，均未验收。249 条应称"格式与模板合格的候选"，各报告自己也是这么写的。 |

**应前移或结构化的检查**【建议】：墙钟稳定性、双视口可读性、`file://` 单文件加载这三项，应同时出现在（a）题面契约文字、（b）fixture 预检、（c）工作区内教师可执行的自检命令、（d）采集后自动判定里，并且四处用同一份代码。跨 trial 与续跑问题应由沙盒隔离消除，而不是事后审计。

### D. 配比与监督：不同口径

来源：`reports/first-sft-20261123-001/{REPORT.md,admission.json,template-audit.json,launch.sh}`，`final-distribution-002.json`，训练运行目录 `${SHARED_DATA}/3d-agent-sft/first-sft-20261123-001/start/output/{args.json,logging.jsonl}` 与 `input/train-index.jsonl`。

**几点判断：**

1. **"首版不监督 thinking"被悄悄改了。**【实测】11-21 计划第 30 行："原始 thinking 完整归档，首版不作为监督目标"。11-22 的组成文档改写为监督"有效 thinking"，最终是 0.5/1/2。我在 `docs/plans/` 和 `decisions.md` 里没有搜到 0.5/1/2 的决策依据。【推断】这组权重可能来自团队预处理工具的默认值，未核实。影响有三：
   - 它让 ReAct 的监督位置占比从 5.0% 变成 10.98%，恰好落进调研建议的"5–20% 自然区间"。**这个"达标"有一半以上是 thinking 贡献的。**
   - 学生被训练去复现教师每条轨迹平均约 3.6 万 token 的思考（9,006,875/249）。Qwen 基线 4 题里 3 题是时间预算耗尽；唯一跑完的一题 3,041 秒输出 60,197 token，约 20 token/秒（n=1）。教师轨迹监督 token 中位数 63,465——【推断】学生若学到教师的篇幅，按这个速度中位数题就要约 3,200 秒，贴着 3600 秒上限。**蒸馏方向与学生的主要失败模式（超时）相冲突。**
   - "天然空 thinking 不监督"（4,243/10,287 个 assistant 段）意味着"这一步不需要想"的决定没有被学到；学到的只是"想的时候怎么想"。
2. **工具调用 ×2 主要加在了整文件代码上。**【实测】按工具调用正文字符：Write 68.3%、Edit 17.3%、Bash 11.6%、Read 2.7%。【推断】ReAct 加权 loss 里约一半是"在 Write 里写整份代码"，与底座的单轮写代码同质；真正的 Agent 决策（查什么、跑什么、改哪里）只占加权 loss 的两成左右。"249 条 ReAct 的加权 token"不等于"249 份 Agent 行为监督"。
3. **batch reduction 使 token 占比不等于梯度占比。**【实测】`micro_batch_size=1`、`global_batch_size=1`、`calculate_per_token_loss=True`、`clip_grad=1.0`；`logging.jsonl` 截至第 4,390 步的 440 条记录中 `grad_norm>1` 的比例是 100%。【推断】每步 loss 是单条样本内的 token 平均，随后梯度被裁到同一范数，再经 Adam（β1=0.9，β2=0.95）——一条 6 万 token 的 ReAct 样本与一条 1.2 万 token 的代码样本对参数的推动量级相同。**更贴近实际的 ReAct 剂量是 2.27% 的更新步，不是 10.98%。** 调研文档里的公式（`3d-agent-data-mix-20261121/README.md` 第三节）描述的就是这个区别：r=63,141/11,922≈5.3，记录占比 2.27% ↔ token 占比 10.98%；只有在大 batch、跨样本按 token 归一时后者才近似梯度占比。未验证环节：我没有读 Swift/Megatron 源码确认 loss_scale 的归一化分母（按 token 数还是按权重和）。
4. **曝光**：1 epoch，每条 ReAct 只见一次，位置由固定种子打乱后基本均匀（各十分位 13–36 条），5 条落在 warmup 内；峰值学习率 1e-6、余弦到 1e-7。
5. **训练日志里一个可用的信号**【推断，基于"日志 loss 为 10 步均值"的假设】：不含 ReAct 行的 10 步窗口平均 loss 从 0.265（前 500 步）降到 0.229（4,000 步后）；含 1 条 ReAct 行的窗口平均约 0.33，反推单条 ReAct 行的 loss 约 1.1–1.3，各阶段没有下降趋势（1.21、1.12、1.17、1.24、1.17）。由于每条只见一次，这相当于同分布留出损失。**到第 4,400 步为止看不到模型在 ReAct 分布上学到东西的迹象。**
6. **训练中没有 ReAct 验证集**：`--val_dataset` 只有 812 条 Aodi 代码验证，且只在最后评一次（`eval_steps=10946`）。

### E. 训练/推理一致性

**训练侧实际长什么样**【实测】：249 条的 system 全部是 `You are a helpful assistant.`；`tools="[]"`；首条 user 是题面 + `OUTPUT_CONTRACT`；assistant 每轮拆成 `<think>…</think>` 段和 `<tool_call><function=…>` 段；工具结果以 `<tool_response>` 包在 user 轮里，图片为 `<image>` 占位。

### F. 评估现状对结论的影响

1. **Qwen 基线只有 4 题**【实测】（`reports/react-teacher-20261121-001/qwen/baseline-final.json`）：`gen-excavator-cycle`、`gen-rocket-mission`、`gen-factory-cells`、`gen-engine-cutaway`，0/4；3 条时间耗尽，1 条因为把阀门开度交成 0..1 数值而断言要求布尔值。这 4 题与训练数据同血缘（它们的 Kimi 交付后来成了 `audit-gen-*`、`edit-gen-*`、`fix-*` 的 fixture），而且**不属于占训练主体的 lab 题型**。所以：既没有"学生在训练题型上原本多差"的数，也没有干净的留出基线。
2. **"512 个 case 全 train"需要更新**：我在给定证据之外发现 `evals/first-sft-holdout-v1/`（`freeze.json`，由 `reports/first-sft-20261123-001/freeze_holdout.py` 于 11-23 凌晨生成，与训练启动同一时段）：18 个新题族、dev 12 / test 48，生成 30、修复 18、编辑 12。这是好事，但有四个限制【实测】：
   - `admission.json` 写明 `browser_baselines: pending`——原生 27B 在这 60 题上一次都没跑过。
   - 题型协议与训练差异很大：英文短题面（规模化训练题是中文）、没有"公开采样表达式"、`assertions: []`，自动检查只有每题族 2 个纯函数取值点（`function_checks`），其余靠人工视觉 rubric。
   - "修复"题是把一行函数从坏公式改成好公式，而正确公式就写在题面里（如 `sample(i,j) returns … i+j+2ij`）。它测不到"根据真实反馈定位并修复"。
   - 独立性只做了关键词不出现的字面检查，报告自己也注明不能证明语义独立。
3. **同源血缘**：42 条 Aodi ReAct 的原题全部在底座 train 里（`first-sft-mix-inputs-20261123-001.json` 的 `in_train: 42`）；规模化 320 题是 1 个谱系分量。任何从这 512 题里抽出来的"验证"都不是留出。
4. **Aodi 协议差异**：原始 one-shot 用 CDN + 静态渲染协议（189/192 可运行），ReAct 用离线 + `renderAt` + `file://`（88/576 技术通过，其中 480 条是契约缺陷）。两个通过率不可比；26 个有配对画面的 case 里原版更好的例子也不少。"ReAct 优于 one-shot"目前没有证据，报告自己也没有这么声称。
5. **Accepted@1 与 pass@3**：教师数据是 pass@3 加人工筛选的产物（B 节）。评估学生必须用单次、全自动门禁；也不能拿学生的 Accepted@1 去对比教师的 66% 入选率——教师自己的单次含门禁通过率大约只有 27–50%。
6. **缺对照**：没有"只用 Aodi 底座、同样超参"的 100:0 对照。Aodi 之前的 one-shot SFT 已经把单轮技术通过从 2/30 提到 21/30（`reports/aodi-one-shot-sft-review-20261121.md`）。所以即使首版学生在 Agent 评估上变好，也无法区分是底座代码数据的功劳还是 249 条 ReAct 的功劳。

## 四、下一版优先级

原则：少而高杠杆；先修"让数据白跑"和"让结论无法成立"的问题，再谈扩量。

### P0

**P0-1 把最终门禁前移成契约、预检和工作区内自检，四处同一份代码**

- 解决的实测问题：248 条漂移排除、136 条可读性排除、480 条 `file://` 契约失败、90 条注定失败的 fixture trial、2 条续跑上下文排除。仅前三类就涉及 864/1,535 条 trial（56%），它们都因契约没写清而未能入选。
- 怎么改：（a）`OUTPUT_CONTRACT` 明确写出"`renderAt(t)` 后状态与像素必须静止""在 640 与 1280 两个视口下机构主体不被面板遮挡""`output/index.html` 必须能以 `file://` 直接打开，不得依赖外部模块文件"；（b）在工作区放一个 `verify` 命令，内部就是采集后判定所用的检查器，教师可以自己跑并拿到真实反馈；（c）fixture 预检用同一个检查器，不通过的 fixture 不进题包；（d）采集器禁止在已有 stream 的目录续跑；（e）修掉 Aodi 题面里"本地/CDN"的矛盾句。
- 如何验证：先跑 20 题 × 1 次的 canary，看采集后门禁失败率；fixture 预检通过率 100% 才放行；Aodi 侧 `file://` 失败率应接近 0。
- 负担：一次性的检查器整合工作；造数量不增加，人工审核量明显下降（漂移与可读性从人工看图变成自动判定加抽查）。

**P0-2 请求级捕获，并用与推理完全相同的模板路径渲染训练数据**

- 解决的实测问题：默认 system、`tools=[]`、2,604 处并行工具结果轮次不一致、257 次无因的记忆文件调用、65.6% 调用含采集机绝对路径、无法证明训练上下文等于教师所见。
- 怎么改：（a）在网关或本地代理层落盘每次请求的 system、tools、messages（密钥不落盘）；（b）训练记录带真实 system 与工具 schema，直接用 `chat_template.jinja`（或确认与其逐 token 等价的路径）渲染；（c）采集沙盒使用中性固定路径（如 `/workspace`），每个 trial 独立的 `CLAUDE_CONFIG_DIR`，关闭自动记忆，不加载用户个人 skills；（d）对现有 249 条，可以用同版本 Claude Code、同参数重放一次请求拿到 system 和 schema 做近似回填，并把记忆文件调用所在的段从监督里去掉。
- 如何验证：取文本和带图各一条 canary，让学生服务端打印渲染后的 prompt，与训练渲染逐 token 比对，差异为 0 才算通过；统计训练集中含 `/kimi/`、`.claude-config` 的调用数为 0。
- 负担：一次性基础设施；（d）不需要新造数。之后的采集没有额外负担。

**P0-3 先把评估和基线跑起来，再决定造什么数据**

- 解决的实测问题：基线只有 4 题且同血缘；holdout 60 题零基线；holdout 与训练题型不同分布；没有底座对照；难度标签没有学生侧证据。
- 怎么改：（a）在 holdout-v1 上跑原生 27B、首版学生，以及 Kimi 单次作为上限参考，统一协议并显式固定压缩窗口、时间上限、effort；（b）补一组"同分布留出"：从 32 个 lab 题族中整族留出若干（连同其装置），回答"在见过的题型上有没有学会"；holdout-v1 回答"能不能迁移"；（c）所有门禁自动化，只报 Accepted@1，另报超时率、每次成功的 token 与耗时、CDN 引用率、未写文件只答代码的比例；（d）加一个只用 Aodi 底座、同超参的对照，哪怕只训到同等步数的一部分；（e）让原生 27B 在候选训练题上先各跑一次，用实测失败来定义"难点"。
- 如何验证：每个对比给出分母和置信区间；48 题 test 只能分辨大差异（约 20 个百分点以上），小差异不下结论。
- 负担：主要是机器时间；造数为零。（b）需要少量新题，但可直接由现有模板生成并整族隔离。holdout-v1 的修复题建议补几道"题面不给正确公式、需要从运行反馈定位"的题，属少量人工。

**P0-4 用"更新步数"设定并报告 ReAct 剂量，并加 ReAct 验证集**

- 解决的实测问题：10.98% 的 token 占比在 batch=1 + 梯度裁剪下只对应 2.27% 的更新；训练过程中没有任何 ReAct 侧的验证信号。
- 怎么改：两条路线任选其一并写明——（a）保持 batch=1，按步数设计配比（例如从当前检查点出发，用 249 条 ReAct 加 1–2 千条抽样底座做第二阶段，使 ReAct 达到 10–20% 的步数；每条重复次数随之透明可见）；（b）改为多条样本累积、跨样本按 token 归一，让 token 占比真正对应梯度占比。同时按题族留出 10–15 条 ReAct 轨迹做验证，定期评估。
- 如何验证：ReAct 留出 loss 是否下降；配合 P0-3 的 Agent 评估；报告里同时列出记录、步数、token、加权 token 四个口径。
- 负担：不需要新数据；需要重新训练或续训一段。

### P1

**P1-1 补上真实修复与编辑，题源用通过新门禁的 fixture**

- 问题：真实缺陷修复最终 0 条、局部编辑 5 条；由真实失败派生的题族全部消失。这与"ReAct 负责观察→修改→复验"的立项理由直接相悖。
- 怎么改：在 P0-1 预检通过的 fixture 上做单缺陷注入（每个缺陷须被检查器拒绝、好版须通过），优先覆盖预实验列出的失败机制（重复渲染不一致、关键时刻出画、暂停恢复、计数逻辑、循环接缝）。
- 验证：每题有"坏版被拒、好版通过"的预检记录；最终集中修复与编辑各自的独立 case 数单列。
- 负担：中等。缺陷注入需要逐类设计，但每类可在多个 fixture 上复用；审核量随 P0-1 自动化而可控。

**P1-2 预先登记的选样规则，取代"最快者优先"**

- 问题：76% 主样本按最短耗时选出；best-of-3 使数据集代表不了单次能力。
- 怎么改：门禁前移后，默认取第 1 次 trial；不合格再看第 2 次，并把"第几次才合格"写进 provenance。多次采样只用于估计稳定性。若 canary 显示单次合格率足够，可把每题采样数降到 1–2。
- 验证：报告教师的含门禁 Accepted@1；主样本 trial 序号分布。
- 负担：降低（trial 数减少三分之一到三分之二）。
