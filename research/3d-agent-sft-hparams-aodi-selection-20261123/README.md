## 核心发现

### 1. 参数选择的实际状态

- **工程约束或有依据**：原版 BF16 起点、180,224 长度覆盖最长 171,524 样本、TP4/PP4、全层重计算、冻结视觉组件、固定数据顺序、恢复 checkpoint，均有配置或 smoke 依据。
- **沿用旧 run 而非新任务调优**：`lr=1e-6`、min LR `1e-7`、cosine、约 3% warmup、Adam 默认项和视觉冻结来自 Aodi 旧配置。旧 run 是 global batch=4、2,591 步，当前为 1、10,946 步，不能直接视为相同优化问题。
- **未经行为对照**：一个 epoch、batch=1 下的 LR、`0.5/1/2` loss、最终 checkpoint 作为默认产物，都没有当前 Agent dev 的选择证据。
- 当时 806 个日志点的梯度范数全部大于 `clip_grad=1`，说明裁剪持续生效。这不是失败证据，但要求把 LR、batch、归一化和裁剪一起分析。
- Aodi 旧实验 step-900 技术通过 **21/30**，step-2591 **20/30**，且题型有得有失。**下一版必须比较中间与最终 checkpoint，不能只看最后一步或 validation loss。**

详细逐项表见[主 Agent 独立报告](main-report.md)。

### 2. Aodi 数据全量审计

本次实际读取 **10,697 train + 812 validation**，不是只看之前抽出的 192 条。

| 实测项目 | 结果 | 含义 |
|---|---:|---|
| Scene-v1 / v2 / GLB train | 3,933 / 3,263 / 3,501 | GLB 占 32.73%，不是附属零头 |
| 题面字符中位数 | 265 / 283 / **37** | GLB 短资产题与复杂长程任务不是同一分布 |
| prompt/answer 精确重复 | **0 组** | 原文及 NFKC/空白规范化均查，含 train/validation 交叉 |
| GLB train 重复标题 | 267 组、1,178 条 | 是同主题不同配置，不是重复答案；适合降权而非硬删 |
| 完整 HTML 闭合 | 三源全部通过 | 结构完整不等于浏览器和语义正确 |
| 原始 192 条运行检查 | 189 可运行 | 每源 64 不能代表所有领域、复杂度、版本和长度 |
| GLB 发布方质量声明 | 全部渲染并验证导出 | 是发布方证据，不等于本地全量复验或 Godot 验收 |

Scene-v1 的复杂度是 1–10 标注，Scene-v2 是课程标签，GLB 没有复杂度；它们都不是 Qwen 实败难度。**不能只保留高层级，也不能把 GLB 短题面直接等同于低价值。** Scene core/r160、GLB addons/多版本和 ReAct 离线/r180/renderAt 的契约差异，比“数据条数够不够”更值得处理。

## Opus 独立复核及联合修正

Opus 最终完成了纯软件示例库的[分层抽样审稿](opus-sampling-review.md)。它只获得已统计事实，没有独立复核训练超参数，也没有重新读取全量原始数据；这部分不能包装成 Opus 对训练配方的认可。

双方一致：

1. 全量池保留，核心集按覆盖构建；同标题变体**降权，不硬去重**。
2. 运行审计按来源、领域、复杂度、长度和版本分层，结构异常样本与随机样本分开统计。
3. 先比较同规模随机核心与分层核心，再比较全量单遍与核心重复到同预算。
4. 当前证据不能证明“全量都必须”“删某个比例更好”或“分层核心已经优于随机”。

Opus 带来的修正：

- **长度要按来源内部的分位数分桶。** 全库统一切长度会让“短”几乎等同于 GLB。
- 不要机械展开成稀疏的 `领域×复杂度×长度` 全交叉小格；预先规定稀疏层合并规则，优先保证 source×domain 和 source×level 的边际覆盖。
- 运行审计若有意过采样高复杂度，要保存抽中概率；估计全池失败率时按包含概率加权，小层报告精确区间，不能把异常定向复核与随机样本混算通过率。
- 随机核心一次抽签可能碰巧偏好或偏差。Opus 建议至少 5 个随机种子形成分布；主 Agent 认为不应直接扩展成 5 次全预算 27B 训练，可在短跑/代理阶段做多种子，若只做单种子则明确标为探索性结果。

调用证据：成功 session `8474b0a5-6e9a-4f45-9caa-b16092fbf90f`，结果 JSON（本地附件未发布） 为 `is_error=false`，`modelUsage` 含 `claude-opus-5-5`。前三次更宽任务均被竞争模型开发风控拒绝，保留原始结果，不换模型冒充联合结论。

## 推荐的下一轮顺序

### P0：先评当前模型，不新增训练

- 原生、当前可用的中后段 checkpoint、最终 checkpoint，在同一 Agent dev 上比较 Accepted@1、题族宏平均、非目标保持、超时和成功 token/耗时。
- Aodi step-900/2591 作为已有参照，分开报告 one-shot 与 Agent 协议。
- dev 用于选择，48 题 test 继续锁定。

### P1：补纯 Aodi 对照

用相同数据顺序槽位、总更新数、batch、长度和 LR schedule，比较 Full-mixed 与 Full-Aodi。纯 Aodi 臂在原 ReAct 槽位替换为预先固定的 Aodi 样本，并记录其额外代码曝光。否则无法判断提升来自一万条代码还是 249 条 ReAct。

### P2：学习率只做一个 coarse probe

在同一 25% 固定数据流上比较 `1e-6` 与 `2e-6`，固定 warmup 比例、decay horizon、batch、裁剪和 UUID，比较 50%/100% checkpoint 的 dev 行为。`2e-6` 是倍率探针，不是文献最优值；差异小于预注册门槛就保留当前值。

**不要把 global batch=4 当作免费提速。** 它会改变流水线、梯度噪声和 loss 归一化窗口；若做，另开优化实验并重新对齐 LR 和来源权重。

### P3：分两步回答“一万条是否都需要”

1. **同规模随机核心 vs 分层核心**：固定 K、ReAct、优化器和更新预算，回答筛选策略是否优于随机。分层核心按来源内部长度分桶、保证领域/复杂度边际覆盖，并限制标题簇权重。
2. **全量单遍 vs 核心重复到同预算**：固定总更新数、ReAct 槽位和 LR schedule，记录每 UUID 曝光。回答独特覆盖是否值得保留，还是少而重复的核心在同算力下更好。

如果 P2 换了 LR，当前全量 run 不能无条件充当 P3 的同配方参考，需要补相应 full reference。短跑只用于淘汰明显差方案，最终胜者仍需全预算与隐藏 test 确认。

### P4：最后做窄 loss 对照

只有失败分类支持时才改一个变量：选工具/读反馈/停止差则试 `Write.content 2→1`；思考冗长则试 thinking `0.5→0`；读图反馈差且有图像利用证据后再考虑视觉解冻。不要同时改数据、LR、batch 和 loss。

## 最终判断

- **全量一万条应当保留为基准和候选池，但不应再被当成“天然必须全部等权”的结论。**
- **精选集值得做，但必须赢过同规模随机核心，并在重复到同预算后与全量比较，才证明筛选没有伤害覆盖。**
- **训练参数下一轮的收益顺序更可能是：行为 checkpoint 选择 → 纯 Aodi 归因 → coarse LR → 数据筛选 → 窄 loss 对照，而不是一上来网格扫参。**

所有数值均是当前数据/日志证据或待检验实验设计；尚无学生完整行为结果，不能提前宣称某配方最优。
