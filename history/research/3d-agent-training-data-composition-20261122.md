# 3D Agent 27B 训练数据组成：通用代码、ReAct 与健康控制

> 公开整理版 · 2026-11-25。历史原文；部分建议已由后续方案替代。 环境路径已泛化，未收录的附件已标注；发布范围见 [整理说明](../../PROVENANCE.md)。

本文记录当前项目从万级 one-shot 起步，逐步形成的训练数据设计。它是当前讨论稿，不替代项目 `decisions.md`，后续以真实实验和生效决定更新。

## 总体理解

**通用代码数据负责“会写 Three.js”；ReAct 轨迹负责“会在沙盒里工作”；健康控制负责“知道什么时候不该改、应该收尾”。**

需要同时区分：

- 已有数据、待采集候选、正式入选数据。
- 独立 case、候选轨迹、最终训练样本。
- 通用代码与 Agent 的有效监督 token 比例，以及 Agent 内部按独立 case 计算的难度比例。

## 一、整体数据表

| 数据层 | 来源与内容 | 监督目标 | 规模建议 | 在训练中的作用 |
|---|---|---|---:|---|
| **通用代码底座** | Aodi 的 CCORE v1/v2/GLB answer-only | 单轮用户要求 → 完整 HTML/JS，不监督独立 thinking | **10,697 train / 812 validation** | 几何、材质、相机、场景组织和代码完整性 |
| **新 ReAct 主样本** | Kimi 在通用 Claude Code 沙盒中的真实多轮轨迹 | 有效 thinking、assistant 正文、工具调用和最终交付；工具结果主要作输入 | 目标 **200–500 个独立 case**，每题默认选 1 条主轨迹 | 观察、修改、复验、长程状态管理和正式交付 |
| **备选轨迹池** | 每题 3 次独立采样 | 不直接全部训练，用于选优和分析波动 | 当前计划约 **1,008 条原始轨迹** | 选出主样本，保留少数实质不同的有效解法 |
| **简单 Agent 任务** | 单常量编辑、离线打包、单个暂停/相机/交付操作 | 最短正确工具路径和停止 | 约占 Agent case **15%** | 防止过度操作，学基本工具契约 |
| **中等 Agent 任务** | 单一故障、一次定向修复、同项复验 | 观察→修改→复验 | 约占 **30%** | 建立可迁移的修复模式 |
| **难点 Agent 任务** | Qwen 可重放失败、Kimi 能完成的长程任务 | 多阶段理解、反馈利用、状态管理和交付 | 约占 **40%** | 提升复杂长程任务能力 |
| **健康控制** | 初始已经合格的场景 | 检查后保持、原样交付、正确阻断 | 约占 **15%** | 防止乱修、虚报错误和无效抛光 |
| **失败/负例池** | 未交付、断言失败、超时、视觉不合格 | **不进入正样本 SFT** | 全量保留 | 诊断、后续修复 fixture、偏好数据候选 |
| **dev/test** | 与训练不同 family 的新任务 | 不作为训练输入 | dev 12 case、test 48 case | 选 checkpoint、测真实泛化 |

比例的第一层，即通用代码与 Agent，按**有效监督 token**计算；第二层，即简单/中等/难点/健康，按**独立 case**计算。两套比例不能混用。

## 三、需要根据预实验设计的长 Agent 问题

新增 ReAct 数据的核心不应该只是随机想“更炫的场景”，而应由真实失败驱动。

| 预实验发现的问题 | 教师任务设计 | 希望模型学到什么 |
|---|---|---|
| **复杂生成超时、未交付**：传送带、挖掘机 | 多阶段装配、机械分拣、长工作循环；要求先有可运行版本再完善 | 分解任务、控制预算、先交付可运行骨架再迭代 |
| **重复渲染不一致**：火箭 `repeat_exact` | 灯光目标残留、rAF 与手动 `renderAt` 冲突 | 识别历史状态泄漏，建立纯时间函数和 A→B→A 复验 |
| **离线 HTML 失效**：太阳能 CORS | 模块文件、import map、外部 bundle 依赖 | 将源码构建为真正自包含 HTML，区分源码可运行与交付可运行 |
| **关键时刻出画**：轨道对接、火箭取景 | 接触、部署、分离等短窗口镜头 | 根据事件调相机，测投影、遮挡和安全边距 |
| **计数或事件逻辑错误**：工厂包裹、铁路道岔 | 传感器到达、整列出清、占用锁闭 | 学真实状态驱动，而不是按时间表播放假动作 |
| **接触与支撑错误**：机械臂、叉车、石拱 | 抓取、装载、装配、撤胎和双手交接 | 测世界坐标、支撑关系和释放时机，避免漂浮和穿插 |
| **时序和循环接缝**：摩天轮、发动机 | 循环速度、相位、恢复和绝对时间 | 检查接缝两侧状态，避免只验证“正在动” |
| **暂停/恢复不完整**：波干涉、太阳能 | 真实点击后时间、像素、draw count 和恢复连续性 | 不只修 `renderAt`，也修真实播放路径 |
| **局部编辑误伤其他状态**：化石、材质、点火、换卡 | 只改一个镜头/参数/对象，保留其余几何与时序 | 非目标保持、同相位差分、最小修改面 |
| **原本已经合格**：健康控制 | 正确拉链、合格火箭、正常场景和正常交互 | 检查后不改、正确交付、避免为了“显得工作”而操作 |
| **输入不足或要求不应执行** | 缺输入、非法开门、非法进路 | 正确阻断，而不是编造资源或强行执行 |

这些任务都应保存：

```text
初始工作区/需求
→ 实际观察或失败反馈
→ 教师的判断和动作
→ 修改后的源码
→ 同项复验
→ 最终自包含交付
```

这比只保留最终 HTML 更接近我们真正想蒸馏的能力。

## 四、三次采样和正式训练样本的关系

每题跑 3 次的目的主要是：

- 判断成功是否稳定，而不是碰巧一次成功。
- 比较不同实现和修复路径。
- 选出质量更高、成本更合理的轨迹。

但它不等于：

- 一个 case 算三个独立 case。
- 三次中成功一次就算 `pass@1`。
- 三条全部进入正样本。

正式使用时：

- 每题默认选择 **1 条主轨迹**。
- 只有实现或返修路径有实质差异时，才保留额外汇本。
- `Accepted@1` 仍按单次自主运行评价，不能用 `pass@3` 美化模型能力。

## 五、训练与验证比例怎么理解

建议采用自然混合，而不是机械复制：

- 约 150 条合格 Agent 轨迹：从 **90:10** 的通用代码 : Agent 有效监督预算起步。
- 约 500 个 case：以 **80:20** 为主，再比较更高或更低剂量。
- 如果自然拼接已经落在约 5–20% 内，不需要为了比例重复或降采样。

如果 Agent 数据过长导致 20% 需要每条重复十几次，就说明应该：

- 降低本轮 Agent 比例。
- 缩小通用代码子集。
- 或继续扩大独立 Agent 池。

## 六、Aodi 数据在当前方案里的准确位置

Aodi 数据仍然可用，但有四个明确角色：

1. **通用代码底座**：提供 Three.js 先验。
2. **已有 one-shot 对照**：step-900、step-2591 可直接评测，避免重复训练。
3. **通用能力回归集**：原 812 validation 用于检查训练后基础代码能力是否退化。
4. **不能替代 ReAct 增量**：它不能提供工具调用、真实反馈、长程状态管理和多轮修复。

另外，CCORE 原始代码和由它派生的 Agent 任务具有血缘关系。**同一源场景及派生变体必须放在同一 split**，不能因为原始 CCORE 在 train，就把它的故障变体放进 test。

最终的数据结构可以概括为：

> **10,697 条通用代码打底，200–500 个独立 ReAct case 主样本塑形，15% 简单任务保效率，15% 健康控制保收尾，40% 真实难点任务提升长程能力，全部用独立题族 dev/test 验证。**
